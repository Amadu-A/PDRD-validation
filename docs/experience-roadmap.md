# Experience Service — дорожная карта

## Назначение

Experience Service отвечает за проверку инженером результатов
автоматического анализа проектной документации.

Система должна сохранять первоначальные замечания VLM,
исправления инженера, решения, подтверждённые координаты
и историю действий.

Конечные результаты разработки:

- рабочий Human Review;
- итоговый Reviewed PDF;
- постоянная база проверенных примеров Experience;
- контролируемая интеграция с поиском E.

## Общие архитектурные правила

Сервис использует существующую инфраструктуру PDRD.

Его таблицы находятся в собственной схеме PostgreSQL `experience`.
Новый PostgreSQL для рабочего проекта не создаётся.

Применяется существующая архитектура Ports and Adapters
с Dependency Injection через Composition Root.

Категории источников N, T, U и E остаются независимыми.
Experience не является нормативным основанием.

Автоматическое предложение координат не считается
подтверждением инженера.

Все действия, влияющие на содержание Review и проверенные
координаты, должны сохраняться с контролем ревизий и аудитом.

## Этап 2. Технический фундамент Experience Service

Статус: ЗАВЕРШЁН.

В рамках этапа реализованы:

- доменная модель Human Review;
- операции Wise, Bad, Edited и Gold;
- сохранение первоначальных замечаний VLM;
- независимые решения по каждому замечанию;
- утверждение законченной редакции Review;
- PostgreSQL-репозиторий со снимками и журналом действий;
- оптимистический контроль конкурентных изменений;
- собственные миграции Alembic;
- типизированные настройки Pydantic;
- каркас FastAPI с liveness и readiness;
- перенос серверной визуализации в proposed_regions;
- проверяющий адаптер исходных серверных артефактов;
- отдельное подтверждение, исправление и отзыв координат;
- хранение подтверждений с независимыми ревизиями и аудитом;
- проверка актуальности подтверждений после редактирования;
- сборка существующих репозиториев и сценариев через DI;
- модульные, архитектурные и интеграционные тесты.

Проверка: 871 passed, 15 skipped в последнем предоставленном
полном серверном quality gate.

Отдельные интеграционные тесты PostgreSQL ранее завершились
результатом 11 passed.

Важно: результаты относятся к проверенному исходному коду.
Они не означают завершения рабочего развёртывания
и сквозного пользовательского сценария.

Этап считается завершением технического фундамента,
а не всего функционала Experience Service.

## Этап 3. Рабочий Human Review и итоговый PDF

Статус: ЗАПЛАНИРОВАН.

Результат этапа: инженер выполняет весь цикл проверки
через интерфейс, его действия сохраняются в PostgreSQL,
а утверждённая редакция используется для итогового PDF.

Необходимые работы:

- подключить доверенный источник заданий API Gateway;
- реализовать серверную идентификацию инженера;
- проверять права доступа к каждому конкретному заданию;
- подключить защищённый HTTP API для операций Review;
- подключить существующий интерфейс к серверному API;
- сохранять решения, исправления и ручные Gold-замечания;
- показывать предложенные координаты отдельно от проверенных;
- позволить подтверждать, перерисовывать и отзывать области;
- обрабатывать конфликты изменений из нескольких вкладок;
- проверять полноту и утверждение текущей редакции;
- формировать Reviewed PDF из утверждённых замечаний;
- сохранять принятые замечания без координат в текстовом отчёте;
- исключать отклонённые замечания из итогового PDF.

Критерий завершения: полный пользовательский сценарий
проходит сквозные тесты с реальным серверным хранением.

Незащищённые бизнес-маршруты публиковать запрещено.

## Этап 4. Постоянная база Experience

Статус: ЗАПЛАНИРОВАН.

Результат этапа: проверенные инженерные решения сохраняются
как воспроизводимые, версионированные примеры.

Необходимые работы:

- сохранять исходный документ и проверенные метаданные;
- создавать crop из оригинального PDF;
- связывать каждый пример с исходным SHA-256;
- сохранять подтверждённые области и provenance;
- проверять актуальность редакции перед записью примеров;
- исключать неподтверждённые координаты;
- предотвращать дублирование примеров;
- реализовать постоянное хранение и историю изменений;
- определить процедуру дополнительного разрешения
  неоднозначных отрицательных примеров.

Edited + Rejected остаётся needs_adjudication до появления
явной процедуры определения причины отклонения.

Критерий завершения: проверенные примеры можно безопасно
сохранять, повторно получать и воспроизводить.

## Этап 5. Индексация Experience и оценка качества

Статус: ЗАПЛАНИРОВАН.

Результат этапа: проверенная база опыта интегрирована
с существующим поиском Knowledge Service.

Необходимые работы:

- согласовать контракт передачи Experience-примеров;
- реализовать повторяемую индексацию;
- использовать существующий shared embedding runtime;
- сохранить разделение нормативных и экспертных источников;
- проверить миграцию и совместимость индексов;
- провести оценку качества на контрольных данных;
- предусмотреть откат при ухудшении результатов.

До выполнения критериев приёмки сохранять:

KNOWLEDGE_SERVICE_SEARCH__EXPERIENCE_ENABLED=false

Включение E допускается только после подтверждённых
результатов испытаний.

До этого момента экспериментальное дообучение VLM
не считается частью работающего производственного контура.

## Правила дальнейшей разработки

Каждый следующий номер обозначает законченный
функциональный результат, а не отдельный файл или коммит.

Работы внутри этапа могут включать несколько файлов
и проверок, но не получают дополнительных номеров этапов.

Перед изменениями обязательно проверять актуальный GitHub,
правила shared-infrastructure и связанные контракты.

Каждый изменяемый файл предоставлять целиком,
с указанием относительного пути.

Новые комментарии и документация должны быть на русском языке.

Каждый этап завершается модульными, интеграционными
и необходимыми сквозными проверками.

Не объявлять этап завершённым исключительно
по результатам модульных тестов.
