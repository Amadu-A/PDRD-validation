# PDRD-validation — согласованный план Human Review и Experience

Дата сверки: 28.09.2026.
Контрольная ветка: feature/experience-base.
Исходный коммит перед этапом 5: `10823b5` (совместимый NumPy для ezdxf).
Проверенная база перед этапом 6: `c1738fe` (серверный Review через Experience API).

## Правила разработки

Сохранять первоначально согласованные этапы 0–9.
Не объединять, не переименовывать и не перенумеровывать их
без отдельного согласования.

Каждый этап — отдельное сообщение с описанием изменённых файлов
и соответствующим циклом проверок. Код изменяется в общей рабочей копии;
по последнему указанию пользователя дублировать файлы в ответе не требуется.

Переходить к следующему этапу только после проверки
результата текущего.

Исправление ошибки не создаёт новый этап или подэтап.

Перед любыми изменениями проверять актуальную ветку и HEAD
GitHub, исходные файлы и действующие правила shared-infrastructure.

В сообщении указывать пути изменённых файлов и команды проверок,
коммита/push на Windows и обновления/проверки на Linux.

Новые комментарии и документацию писать на русском языке.

Сохранять существующую архитектуру, DI, разделение N/T/U/E
и принятые инфраструктурные ограничения.

## 2. Frontend: геометрия

Первоначальная задача:

Ручное выделение ошибки, размещение карточки
и соединителя на одном листе.
Редактирование и отмена действий.

Статус: РЕАЛИЗОВАН В ЛОКАЛЬНОМ UI.

Реализованы:

- выделение области ошибки;
- размещение текстовой карточки;
- соединитель между областью и карточкой;
- работа в пределах одного листа;
- отмена незавершённого выделения;
- редактирование текста ручного замечания;
- растягивание сторон и углов области ошибки и карточки для Gold и VLM;
- сохранение размера при отпускании указателя, Esc для отмены жеста;
- поддержка изменения границ стрелками с клавиатуры;
- отклонение красным крестиком со скрытием рамки, линии и текстовой карточки;
- сохранение отклонённого замечания в операционном локальном снимке;
- отмена добавления, изменения областей и решения, отдельно для каждого листа;
- модульные проверки геометрии.

Отмена черновика не меняет сохранённую геометрию и решение.
Применение другой геометрии (в том числе через отмену действия)
сбрасывает решение в pending и требует повторной проверки.
Тег gold сохраняется. Undo отклонения возвращает прежнее решение,
рамку, соединитель и текстовую карточку. Ревизии решений возрастают.
В групповой карточке скрывается только отклонённый подпункт со своей
рамкой и линией; общая карточка скрывается после отклонения всех подпунктов.
Изменение размера общей карточки требует нового решения для видимых подпунктов.
Кнопки геометрии и отдельного удаления убраны. Кнопки решений уменьшены на 25%.
История очищается при открытии другого отчёта.

Серверное сохранение операций подключено в этапе 5.
Крестик означает rejected, запись остаётся в Human Review для аудита.
Только Undo создания локального Gold отменяет саму добавленную запись.
В серверном режиме эта отмена записывает rejected и сохраняет аудит.
Прокрутка внутри карточки убрана; полный ответ доступен во внешнем тултипе.
Области, изменённые в браузере, остаются предложениями и не считаются
подтверждёнными серверными координатами VLM.
Исключение rejected из итогового Reviewed PDF реализовано на этапе 6;
существующий автоматический PDF решения локального UI не применяет.

## 5. Review API

Первоначальная задача:

Маршруты и адаптеры Gateway, сохранение решений
и редактирования, повторное получение состояния
после перезагрузки.

Статус: РЕАЛИЗОВАН И ПРОВЕРЕН НА WINDOWS И LINUX.

Существующие OpenReview/ChangeReview и PostgreSQL-репозитории соединены
через Gateway → отдельный Experience Service. Исходный PDF, результат,
полные тексты/основания и предложения координат читает серверный адаптер.
Браузер не задаёт оригиналы, теги, actor или идентичность документа.

Реализованы открытие, чтение, строгие команды add/edit/decide/reset/geometry/approve,
CAS, история решений, восстановление VLM и Gold, обеих областей и полного списка.
Очередь последовательная; потерянные ответы и конфликты не вызывают дублирования.
Ошибки записи блокируют правки и сохраняют несохранённое состояние на странице.
Полный набор сценариев и запуск: [review-api.md](review-api.md).

Предусмотрены порты получения серверного контекста и проверки доступа
для будущей авторизации. Сейчас используется настроенный оператор закрытого UI.

Контекст определяет выполняющего операцию, запрошенное job_id
и точку проверки доступа к заданию и операции. Actor берётся
из серверного адаптера, а не из JSON или произвольного заголовка браузера.

Не реализовывать в рамках этого этапа
полноценную регистрацию, админку,
управление пользователями или сессиями.

До подключения реальной аутентификации
использовать контролируемое тестовое окружение.
Не публиковать незащищённый бизнес-API.

Профиль `review` запускает приватный frontend на 127.0.0.1:8081,
Experience без опубликованного порта и отдельный запуск миграции.
Два служебных ключа остаются между контейнерами. Основной frontend 8080
не получает доступ к записи Review. Полноценная авторизация не реализована.

Критерий завершения:

Решения, исправления и подтверждения
сохраняются и восстанавливаются через
серверный API в контролируемых проверках.

Подтверждение решения и подтверждение области независимы. API сохранения
геометрии не вызывает ConfirmArea и не повышает браузерные координаты
до подтверждённых VLM. Серверный контур ConfirmArea/RevokeArea существует;
Явный пользовательский сценарий подтверждения/отзыва подключён в этапе 6.
Реальный SQL/Docker-прогон выполняется на Linux; Windows daemon
в текущей сессии недоступен.

Проверка этапа 5 на Windows: Ruff check/format и pip check успешны;
общий набор — 914 passed, 16 skipped без предупреждений; JavaScript — 68 passed.
Отдельно в браузере проверены отсутствие скролла карточки, полный тултип,
восстановление принятой VLM-находки и Gold на листе и в полном текстовом списке.
Схема Compose профилей review/test проверена без запуска контейнеров.
По предоставленным Linux-логам те же общие тесты прошли на сервере,
изолированный PostgreSQL — 12 passed; миграция `20260928_0002` актуальна.
Experience и Gateway healthy, приватный frontend доступен на 127.0.0.1:8081.
Режимы 8080/8081 проверены HTTP-запросами. Это подтверждение развёртывания
этапа 5; новая реализация этапа 6 проверяется отдельно.

## 6. PDF с подтверждением

Первоначальная задача:

Серверная проверка всех решений,
формирование PDF только из одобренных замечаний,
корректная инвалидизация кеша.

Статус: РЕАЛИЗОВАН В КОДЕ; ПРОВЕРКА ОБНОВЛЕНИЯ НА LINUX И В РАБОЧЕМ UI ПРЕДСТОИТ.

Реализованы:

- серверная проекция актуального утверждённого Review в Experience;
- явные команды `confirm_area`/`revoke_area` с собственными версиями и аудитом;
- отдельная кнопка подтверждения области VLM в полном текстовом списке;
- кнопка утверждения и скачивания через общую последовательную очередь;
- закрытый маршрут Gateway `POST /api/v1/analyses/{job_id}/reviewed-pdf`;
- проверка документа и SHA-256 исходного PDF;
- исключение rejected из аннотаций и текстового приложения;
- полный текст всех принятых замечаний, включая замечания без области;
- жёлтый Gold на заданном физическом листе и в итоговом текстовом списке;
- отдельный кеш с редакцией Review, подписью подтверждений, источником и версией рендерера;
- повторная проверка проекции и источника перед выдачей, включая попадание в кеш.

При `pending` или устаревшем утверждении экспорт блокируется сервером и UI.
Принятая VLM без подтверждённой области получает только текстовую запись.
`proposed_regions` и операционные правки браузера сами по себе не подтверждают
координаты. После изменения текста/геометрии прежнее подтверждение устаревает.
Подтверждение/отзыв области меняет ключ PDF даже без изменения ревизии Review.
Изменение данных во время формирования вызывает `409`, а не выдачу прежнего PDF.

Автоматический PDF остаётся отдельным результатом исходного анализа.
Crop и сохранение постоянных Experience records не входят в экспорт.
Новой DDL-миграции нет: вершина остаётся `20260928_0002`.
Контракт, сценарии проверки и запуск: [review-api.md](review-api.md).

Контрольная точка этапа 6 на Windows: общий quality gate — 965 passed,
18 skipped; все JavaScript suites — 89 passed. Ruff check и format check
успешны (585 файлов), `pip check` и `git diff --check` пройдены.
В Chrome с действующими Gateway → Experience → Document ASGI-маршрутами
проверены подтверждение области, Wise/Bad/Gold, скачивание итогового PDF
и восстановление Review. Сгенерированный PDF проверен визуально.

Общие Linux-тесты, изолированный PostgreSQL и развёртывание именно этапа 6
ещё не выполнялись: локальный Docker daemon недоступен. Они остаются
следующей проверкой по `ops/deploy-reviewed-pdf.sh` на сервере пользователя;
результаты этапа 5 не заменяют этот прогон.

## 7. Experienced User Base

Первоначальная задача:

Постоянное хранение вырезанных областей
и метаданных, полноценная страница CRUD,
поиск, фильтрация и экспорт.

Статус: ПРЕДСТОИТ.

Демонстрационная страница существует.
Постоянный каталог ещё не реализован.

Использовать подтверждённые координаты
и оригинальный документ.

Хранить происхождение, редакции,
первоначальный текст и исправления.

Не смешивать предварительный отбор кандидатов
с окончательным сохранением Experience.

Уточнённое правило отбора (по последнему решению пользователя):

Edited + Rejected сохраняется с обоими текстами, координатами,
решением и историей. needs_adjudication приостанавливает автоматическое
обучение: пока не определено, отрицательным является исходный текст VLM,
исправленный текст или оба. Это согласованная защита, а не расхождение.
До индексации добавляется явная причина отказа и определяется
объект отрицательной разметки. Автоматически менять статус на negative нельзя.

## 9. Подготовка fine-tuning

Первоначальная задача:

Версионирование датасета, положительные
и отрицательные примеры, отдельная оценка
и эксперимент дообучения.

Статус: ПРЕДСТОИТ.

## Отдельная будущая работа: пользователи и права

Это направление не заменяет этапы 0–9
и не получает новый номер без согласования.

В рамках Review API сейчас закладывается
архитектурный контракт серверного контекста пользователя.

аутентификацию, управление сессиями и правами
разрабатываем позднее, по отдельному согласованию.

нельзя открывать операции изменения Review
произвольным внешним пользователям.
