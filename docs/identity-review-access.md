# Назначение доступа к ревью

В админке рядом с каждым пользователем находится галочка «Доступ к ревью».
Она сохраняется сразу, отдельной командой от роли и назначений разделов.

| Пользователь | Доступ |
| --- | --- |
| Активный руководитель отдела или администратор | Автоматически включён, галочка недоступна для снятия |
| Активный проектировщик | По назначению администратора; по умолчанию выключен |
| Гость, неподтверждённый, заблокированный, без рабочей роли | Ревью недоступно |

Ручное назначение даёт проектировщику полное ревью **собственных** анализов:
Gold, правки текста и областей, принятие/отклонение, сохранение решений,
утверждение и скачивание итогового PDF, перенос замечаний в Experience.
Назначение не даёт доступа к чужим заданиям, управлению разделами, версиями
Experience или админке. Для руководителя сохраняется существующая проверка
области полномочий. Просмотр общего каталога Experience остаётся доступным
руководителю и администратору по действующей политике.

Автоматический доступ вычисляется по действующим ролям, статусу, срокам и
членству. Ручной флаг хранится отдельно: повышение роли не включает его.
После понижения руководителя до проектировщика действует только ранее явно
выданное ручное назначение; если его не было, ревью закрыто.

## Хранение и API

User Service владеет полем `users.accounts.review_access_enabled` и аудитом
`users.review_access_events` (актёр, профиль, новое значение, версия и время).
Миграция User Service: `20261006_0005`. Она оставляет проектировщикам значение
`false`; руководители и админы получают автоматическое право без ручного флага.

`PATCH /api/v1/admin/users/{user_id}/review-access` принимает
`{"enabled": true, "authorization_version": 2}`. Admin Service проверяет
живую сессию и CSRF, а затем передаёт актёра из Auth Service через закрытый API
User Service. Сервисный ключ и административная роль повторно проверяются.
Нельзя передавать роль, источник прав или ручной флаг в регистрацию/вход.

Флаг, версия прав и аудит изменяются атомарно. Повтор того же значения с текущей
версией ничего не меняет. Устаревшая версия возвращает 409; интерфейс требует
обновления списка и не повторяет назначение автоматически.

**После выдачи или отзыва пользователю нужно войти повторно.** Версия полномочий
повышается, и ранее открытые сессии отклоняются Auth Service. Сервер проверяет
операционные права и владельца задания при каждом запросе, поэтому открытая
вкладка не сохраняет возможность правок после отзыва.

HTTPS, Secure/HttpOnly cookie, CSRF, строгий Origin и правила хранения AD-пароля
сохраняются. Настройки TLS и `.env` для этого обновления менять не требуется.

## Windows: проверки и публикация вручную

Из корня проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\ops\check-quality.ps1
if ($LASTEXITCODE -ne 0) { throw "Проверки качества не прошли" }
git diff --check
if ($LASTEXITCODE -ne 0) { throw "Ошибка diff" }
git status --short
git diff
```

После просмотра результата и новых файлов:

```powershell
git add -- frontend services/user-service services/admin-service services/api-gateway/tests/functional/test_review_access_permissions.py tests/architecture/test_review_access_boundaries.py docs/identity-review-access.md docs/identity-catalog-experience.md docs/identity-personal-account.md
if ($LASTEXITCODE -ne 0) { throw "Не удалось добавить файлы" }
git commit -m "Добавить назначение доступа к ревью в админке"
if ($LASTEXITCODE -ne 0) { throw "Коммит не создан" }
git push origin feature/auth-user-admin
if ($LASTEXITCODE -ne 0) { throw "Проверьте отправку в оба репозитория origin" }
```

У origin настроены два адреса отправки; `git remote get-url --push --all origin`
должен показать публичный и приватный репозитории. Коммит и push выполняет пользователь.

## Сервер: интеграционные тесты и обновление

Одна команда целиком; скрипт останавливается при первом отказе.
User runner использует изолированный PostgreSQL и проверяет миграции,
конкурентный CAS, аудит, откаты и недействительность старых сессий.

```bash
bash <<'BASH'
set -euo pipefail
cd "$HOME/projects/PDRD-validation"
git pull --ff-only origin feature/auth-user-admin
docker compose -f ops/compose.user-test.yaml up --build --abort-on-container-exit --exit-code-from user-test-runner
docker compose -f ops/compose.user-test.yaml down
bash scripts/up.sh
bash scripts/check-stack.sh
docker compose --profile identity --profile auth exec -T user-service python -m alembic -c alembic.ini current --check-heads --verbose
BASH
```

Ожидаемая ревизия User: `20261006_0005 (head)`. `up.sh` применяет миграции и
пересобирает активные профили; в `.env` должны оставаться `identity,auth,review`
и другие используемые профили. Изменённые User, Admin и frontend обновляются
вместе. При ошибке runner или пересборки не переходите к следующему шагу.

## Ручная приёмка

1. Через `https://pdrd.itcneoterm.local/` войдите администратором. В списке
   пользователей галочки руководителей и админов включены и заблокированы
   с подписью «По роли». У проектировщика галочка редактируется.
2. До выдачи доступа проектировщик запускает обычный PDF/CAD и читает результат,
   но не получает возможности править и сохранять ревью.
3. Поставьте ему галочку. После повторного входа откройте собственный анализ:
   правки текста/областей, Gold, принятие/отклонение работают и сохраняются.
   Обновите страницу — сохранённые решения восстанавливаются.
4. Разберите все замечания, скачайте итоговый PDF. Принятые замечания перенесены
   в Experience; руководителем или админом проверьте их автора в каталоге.
5. Снимите галочку при открытой вкладке проектировщика. Следующая защищённая
   операция требует входа; после повторного входа правки недоступны.
   Обычный анализ остаётся рабочим.
6. Выданный доступ не открывает чужой анализ, админку и версии Experience.
   Повышение до руководителя включает галочку автоматически; понижение без
   прежнего ручного назначения закрывает ревью.
7. В двух вкладках админки измените один профиль. Устаревшая вкладка получает
   сообщение об изменённых правах, не затирая последнее назначение.
