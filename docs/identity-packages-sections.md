# Приёмка обычного анализа, личных пакетов и доступа к разделам

## Модель доступа

Обычный PDF/CAD запускается без нормативного раздела у гостя и активного
авторизованного пользователя. Без выбранных личных документов фронт вообще
не отправляет `user_package_document_ids`. Старый клиент с `[]` также допустим.

Knowledge Service остаётся единственным источником UUID и названий разделов.
Админка показывает этот живой каталог вместо формы создания отделов. В карточке
пользователя отмечаются несколько разделов; роль, назначения, аудит и новая
`authorization_version` записываются одной транзакцией User Service. Несовпадение
ожидаемой версии даёт 409. После изменения доступа пользователь входит повторно.
Администратор имеет доступ ко всем нормативным разделам.

Личные пакеты активного пользователя доступны в назначенных разделах. Владелец
категории и документа хранится в Knowledge Service как `owner_user_id` без FK
в чужую схему. Gateway получает UUID только из подтверждённой сессии и проверяет
раздел и владельца. Браузер не передаёт владельца; подмена заголовка или параметра
не меняет серверный контекст. Чужие UUID не позволяют читать PDF или изменять
пакет. Общие нормативные маршруты также не раскрывают личные документы.

Перед созданием задания Gateway проверяет выбранные готовые документы владельца
и фиксирует их UUID и рабочий промпт в снимке анализа. Knowledge Service получает
только выбранные UUID; раздел без пакетных UUID не запускает поиск по всем пакетам.
Руководитель и администратор видят свои пакеты. Совместный доступ по отделу пока
не предоставляется. Старые записи без владельца скрыты; случайному пользователю
они не назначаются. Миграция не удаляет их файлы.

Рабочий промпт можно менять для собственного анализа в назначенном разделе.
Кнопка сохранения общего системного промпта требует `system_prompt.manage`.
Изменение рабочего текста не переписывает общий системный промпт.

HTTPS, строгий Origin, защита от CSRF, Secure/HttpOnly cookie и отсутствие
хранения пароля AD сохранены. Публичный адрес: https://pdrd.itcneoterm.local/.
Внешний корпоративный TLS proxy продолжает работать с существующим frontend.

## Проверка на Windows

В активированной `.venv` из корня проекта:

```powershell
$env:PYTHONPATH = (Get-ChildItem services -Directory | ForEach-Object { Join-Path $_.FullName 'src' }) -join ';'
python -m ruff check .
python -m ruff format --check .
python -m pytest -q --import-mode=importlib
npm.cmd --prefix frontend test
git diff --check
```

Реальные БД в этом прогоне пропускаются. Их проверяют изолированными Compose
окружениями: `ops/compose.user-test.yaml` и `ops/compose.knowledge-test.yaml`.
Они не публикуют порты и используют временные PostgreSQL без рабочих томов.

## Обновление aistation

После успешных проверок, коммита и push пользователя:

```bash
cd ~/projects/PDRD-validation || exit 1
git status --short
git pull --ff-only origin feature/auth-user-admin
```

Следующий блок выполняется как отдельный сценарий и прекращается при ошибке:

```bash
bash <<'BASH'
set -euo pipefail
cd ~/projects/PDRD-validation
run_database_tests() {
    local config="$1" runner="$2" result=0
    docker compose -f "$config" up --build --abort-on-container-exit --exit-code-from "$runner" || result=$?
    docker compose -f "$config" down
    return "$result"
}
run_database_tests ops/compose.user-test.yaml user-test-runner
run_database_tests ops/compose.knowledge-test.yaml knowledge-test-runner
bash scripts/up.sh
bash scripts/check-stack.sh
BASH
```

`up.sh` читает закрытый `.env`, сохраняет выбранные COMPOSE_PROFILES,
пересобирает сервисы и применяет миграции. Нужны прежние `identity,auth` и
остальные используемые профили. Новая настройка административного клиента:
`ADMIN_SERVICE_KNOWLEDGE_SERVICE_URL=http://knowledge-service:8401`; значение
по умолчанию уже задано в Compose. Сертификат и корпоративный TLS proxy
этими тестовыми окружениями не изменяются.

## Ручная приёмка

1. Открыть HTTPS-адрес и обновить страницу без кеша. Гостем запустить PDF без
   раздела, затем CAD без раздела: задание создаётся без 403 и без требования
   выбрать раздел. Проверить готовый отчёт после ответа модели.
2. Войти и повторить оба обычных анализа. В Network поле
   `user_package_document_ids` отсутствует, если пакеты не выбраны.
3. В админке справочник показывает те же разделы, что главная страница.
   Переименование раздела на главной отражается после обновления справочника.
   Формы создания отдельного отдела нет.
4. В карточке сотрудника отметить два раздела и сохранить роль и доступ.
   После повторного входа сотрудник видит назначенные разделы. Прямой запрос
   к неназначенному разделу получает 403. Обычный анализ без раздела доступен.
5. В назначенном разделе создать личный пакет, загрузить PDF/DOC/DOCX,
   дождаться готовности индексации, отметить документ и запустить анализ.
   Проверить, что в запросе есть только выбранные пакетные UUID, а в отчёте
   при релевантном поиске появляются источники U.
6. Другим пользователем проверить, что первый пакет не виден. Прямые ссылки
   на чужой документ и попытки удаления отклоняются. Руководитель и администратор
   также не получают чужие личные пакеты по своей роли.
7. Изменить рабочий промпт и запустить анализ. Общий системный текст сохраняется
   только пользователем с правом управления промптом. Переключение разделов,
   выход и смена аккаунта не оставляют чужие выборки или рабочий текст.
8. Открыть одну карточку пользователя в двух вкладках: сохранение устаревшей
   версии получает 409 и требует загрузить актуальные данные.

Автотесты не заменяют серверную проверку VLM, LDAPS, SMTP и полного анализа файла.
