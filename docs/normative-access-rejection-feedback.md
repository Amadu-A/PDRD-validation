# Удаление нормативных объектов и причины отклонения замечаний

## Назначение доступа к нормативному блоку

В админке у пользователя есть галочка «Доступ к изменению нормативного блока».
Она добавляет право `normative.delete`: удаление отдельных нормативных документов
и разделов в области доступа пользователя. Создание, загрузка и переименование
сохраняют прежние правила `normative.write`.

| Роль | Создание и переименование | Удаление |
| --- | --- | --- |
| Администратор | Доступно | Автоматически; галочка включена и заблокирована |
| Активный руководитель | Доступно | После явного назначения администратором |
| Активный проектировщик | Недоступно | После явного назначения администратором |
| Гость, бесплатный или заблокированный профиль | Недоступно | Недоступно |

Назначение не открывает чужие разделы, админку, Review и управление промптами.
Gateway проверяет операционное право и назначенный раздел перед удалением.
Удаление раздела использует существующий идемпотентный сценарий Knowledge:
очистку документов, PDF и точек Qdrant с возможностью повторить операцию после сбоя.

User Service хранит `users.accounts.normative_access_enabled`, по умолчанию
`false`, и аудит в `users.normative_access_events`. Автоматическое право админа
вычисляется по живой роли и не записывается в ручной флаг. После понижения роли
действует только ранее явно выданный флаг.

Публичный маршрут: `PATCH /api/v1/admin/users/{user_id}/normative-access`.
Команда: `{"enabled": true, "authorization_version": 2}`. Admin Service проверяет
сессию и CSRF; приватный маршрут User Service повторно проверяет служебный ключ,
доверенного актёра и действующую административную роль.

Флаг, версия прав и аудит фиксируются одной транзакцией. Повтор того же значения
по актуальной версии ничего не меняет. Устаревшая версия возвращает 409.
**После выдачи и отзыва пользователь входит повторно:** прежние сессии теряют
актуальную версию полномочий. Открытая вкладка не сохраняет отозванное право.

## Причины отказа в Review и Experience

Красный крестик открывает диалог «Отклонить замечание».
До подтверждения форма не меняет решение. «Отмена» и Escape закрывают её без записи.
Причина обязательна; комментарий необязателен и ограничен 2000 символами.

| Подпись интерфейса | `reason_category` |
| --- | --- |
| Замечание ошибочное | `false_positive` |
| Дублируется | `duplicate` |
| Неверно определён объект | `misunderstood_drawing` |
| Неверно определено место | `wrong_location` |
| Неверно применён норматив | `wrong_normative_basis` |
| Требование неприменимо | `not_applicable` |
| Другая причина | `other` |

Пример команды Review (после проверки сессии, Origin и CSRF):

```json
{
  "action": "decide",
  "expected_revision": 3,
  "finding_id": "vlm:1",
  "decision": "rejected",
  "reason_category": "false_positive",
  "comment": "Это резервный насос, значение корректно"
}
```

Gateway и Experience Service проверяют одинаковый строгий контракт; домен
повторяет проверку причины. Браузер не задаёт автора, оригинал или тег.
Категория и комментарий входят в текущий снимок, события аудита до/после действия
и доверенный источник Experience. Изменение объяснения уже отклонённого замечания
создаёт новую редакцию; одинаковое повторение не дублирует историю.

Принятие, сброс решения, правка текста или геометрии очищают текущие поля отказа,
сохраняя прежние объяснения в аудите. Undo восстанавливает прежнюю причину.
Если прежний отказ относится к старой записи без причины, UI просит выбрать её
перед новым сохранением отказа.

После утверждения Review объяснение доступно в таблице Experience и в
`source.reason_category`/`source.comment` API. ZIP каталога содержит эти поля
в `manifest.json` и отдельные колонки CSV. CSV экранирует потенциальные формулы.
Объяснения также входят в новые проекции векторного индекса и снимки подготовки
дообучения. Разные объяснения одинакового замечания различают примеры при
семантическом объединении, чтобы не терять пользовательскую обратную связь.

`rejection_reason` и `negative_target` каталога сохраняют прежнее назначение:
инженерную оценку неоднозначного `edited + rejected`. Категория из Review
не выбирает автоматически, какой текст считать отрицательным примером.
Отсутствие пригодной области по-прежнему исключает запись из индекса.

Старые JSONB-снимки читаются с `reason_category=null`, `comment=""`; им не
приписывается выдуманная причина. Для новых отказов категория обязательна.
Новые поля не требуют изменения структуры JSONB. Миграция Experience
`20261006_0006` согласует технический `content_key` с причиной и комментарием.
Она обновляет только ключи строк с категорией, сохраняя снимки, редакции и аудит.
Историческая миграция `0005` остаётся неизменной. Старые версии датасетов остаются неизменными;
для включения новой обратной связи нужно сохранить новую версию.

## Проверки и публикация на Windows

Коммит и отправку выполняет пользователь. Из корня проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\ops\check-quality.ps1
if ($LASTEXITCODE -ne 0) { throw "Проверки качества не прошли" }
git diff --check
if ($LASTEXITCODE -ne 0) { throw "Ошибка diff" }
git status --short
git diff
```

После просмотра изменений и новых файлов:

```powershell
git add -- frontend services tests docs
if ($LASTEXITCODE -ne 0) { throw "Не удалось добавить файлы" }
git commit -m "Добавить доступ к удалению нормативов и причины отклонения замечаний"
if ($LASTEXITCODE -ne 0) { throw "Коммит не создан" }
git remote get-url --push --all origin
git push origin feature/auth-user-admin
if ($LASTEXITCODE -ne 0) { throw "Проверьте отправку в оба репозитория origin" }
```

У origin настроены два адреса отправки: публичный и приватный репозитории.

## Тесты и обновление на aistation

Команда останавливается при первом отказе. Изолированные тестовые контейнеры
не используют рабочую БД, volumes, сеть или секреты.

```bash
bash <<'BASH'
set -euo pipefail
cd "$HOME/projects/PDRD-validation"
git pull --ff-only origin feature/auth-user-admin
docker compose -f ops/compose.user-test.yaml up --build --abort-on-container-exit --exit-code-from user-test-runner
docker compose -f ops/compose.user-test.yaml down
docker compose -p pdrd-experience-test -f ops/compose.experience-test.yaml up --build --abort-on-container-exit --exit-code-from experience-test-runner
docker compose -p pdrd-experience-test -f ops/compose.experience-test.yaml down
bash scripts/up.sh
bash scripts/check-stack.sh
docker compose --profile identity --profile auth exec -T user-service python -m alembic -c alembic.ini current --check-heads --verbose
BASH
```

Ожидаемая ревизия User: `20261006_0006 (head)`. Предыдущая `0005` отвечает за Review,
новая `0006` — за удаление нормативных объектов. Experience обновляется до
`20261006_0006`. `up.sh` применяет миграции и пересобирает активные профили.
В `.env` сохраняются `identity,auth,review` и остальные используемые профили.
Обновляются User, Admin, Gateway, Experience и frontend вместе.
Настройки HTTPS, Secure cookie, CSRF и строгого Origin сохраняются.

## Ручная приёмка

1. На `https://pdrd.itcneoterm.local/` войдите администратором. Новая галочка
   у админа включена «По роли», у руководителя и проектировщика по умолчанию выключена.
2. Руководитель без галочки создаёт и переименовывает раздел, но не удаляет его.
   Выдайте галочку, войдите этим пользователем снова: появляются удаления
   отдельных документов и раздела. У проектировщика галочка открывает удаление,
   сохраняя отсутствие создания и переименования.
3. Используйте только тестовый раздел. После удаления проверьте исчезновение
   его документов, PDF и точек Qdrant. Прямой DELETE чужого раздела должен
   вернуть 403 даже с галочкой. Повтор после временного сбоя должен завершить очистку.
4. Отзовите право при открытой вкладке. Следующая защищённая операция потребует
   входа; после него удаление недоступно. Права создания руководителя сохраняются.
5. Пользователем с Review откройте собственный анализ. Нажмите красный крестик:
   диалог содержит семь причин. Отмена и Escape сохраняют прежнее решение.
   Без выбранной причины отказ не записывается.
6. Выберите причину и введите «Это резервный насос, значение корректно».
   Подтвердите отказ: карточка и текст скрыты в обоих представлениях.
   Обновите страницу и проверьте восстановление решения; Undo возвращает
   предыдущее решение. Принятие или новая правка не переносят старую причину.
7. Повторно отклоните замечание, завершите решения по всем замечаниям и утвердите
   Review. В Experience видны причина и комментарий. В ZIP проверьте JSON и CSV.
   Отклонённое замечание отсутствует в итоговом PDF. Старые примеры открываются.
8. Обычный PDF/CAD, вход, личные пакеты, промпты и прежние возможности Review
   должны продолжать работать. Пользователь без доступа к Review не получает
   права отклонения через новую форму.

## Если обновление остановилось на тесте старого Bad

Ошибка `test_legacy_bad_migration_and_repeated_pdf_repair_without_duplicate`
с `AttributeError: NoneType ... example` означает несовпадение технических ключей
после повторного применения миграции `0005` к снимку с причиной отказа.
Причина учитывается текущим доменом, но отсутствует в историческом алгоритме.
Это исправлено новой миграцией `20261006_0006`; старый алгоритм не переписывается.

При таком отказе `set -e` завершает блок до `scripts/up.sh`. Pull выполнен,
но рабочие контейнеры этим блоком ещё не пересобраны. После публикации исправления
повторите тест Experience; затем выполните обычное обновление стека.
Ошибки ограничения уникальности и внешнего ключа в логах тестового PostgreSQL
ожидаемы в сценариях проверки защиты. Итоговый результат pytest и код runner
определяют, завершились ли тесты успешно.
