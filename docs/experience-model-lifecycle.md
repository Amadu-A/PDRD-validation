# Индексация Experience, дообучение VLM и применение версий

Дата сверки кода: 29.09.2026. Последняя подтверждённая сервером база:
`e20230f`; функции `b1ba688` ещё требуют полного gate и приёмки Linux.

Документ объясняет текущие ограничения интерфейса и следующий цикл разработки.
Пути будущих артефактов ниже являются предложением: соответствующих volumes,
training worker и загрузки адаптеров в текущем Compose ещё нет.

## Что уже работает

| Действие | Результат | Меняет веса модели |
|---|---|---|
| Индексация выбранных замечаний | Embedding текстов и crop, новая коллекция Qdrant, фиксированный состав версии | Нет |
| Подготовка набора для дообучения | Снимки выбранных редакций, тексты, разметка, ссылки на crop и SHA-256 manifest | Нет |
| Выгрузка выбранной версии | ZIP с зафиксированными текстами, разметкой и PNG; текущий каталог не переписывает снимок | Нет |
| Просмотр версии | Подсветка состава и просмотр сведений | Нет |
| Загрузка/отзыв отчёта качества | Проверка независимой оценки, аудит и серверный допуск готовой векторной версии | Нет |
| Назначение векторной версии | Запись `applied_artifacts` после допуска; рабочий поиск Knowledge читает её по разделу при включённом E | Нет |

Векторизацию выполняет Knowledge через существующий `shared-embedding`.
Embedding-модель при этом не переобучается. Каждая версия использует отдельную
коллекцию `pdrd_e_<embedding_identity>_<version_uuid_without_hyphens>`.
Её данные находятся в существующем volume `qdrant_data`, внутри контейнера
Qdrant — `/qdrant/storage`. Volume `experience_crops` хранит PNG оригинальных
областей, а не веса моделей.

Набор `fine_tune` получает статус `prepared`. Это подготовленные данные;
`weights_sha256` пока пуст. Кнопка подготовки не запускает GPU-обучение.

## Условия рабочего применения векторной версии

`ready` подтверждает успешную сборку коллекции. Допуск использования в анализе
проверяется отдельно: сервер требует `quality_approved=true`.
Для дообученной модели дополнительно требуется SHA-256 настоящих весов.
Worker индексации не может присвоить допуск качества.

В `b1ba688` Experience принимает JSON-отчёт для точных `version_id`,
`manifest_sha256`, модели, раздела, размерности и коллекции и пересчитывает
допуск по заявленным метрикам. Сам HTTP-приём не воспроизводит VLM-эксперимент.
Отзыв допуска снимает назначение. Knowledge читает назначенную версию
раздела до и после поиска, проверяет совместимость отчёта и не обращается к
старой коллекции при отсутствии назначения. Три n8n workflows передают
нормативный `section_id` в запрос E; их требуется вручную загрузить и
опубликовать в n8n.

`KNOWLEDGE_SERVICE_SEARCH__EXPERIENCE_ENABLED=false` сохраняется до независимой
оценки и серверной проверки. Пользователь подтвердил, что отложенного размеченного
набора пока нет.
Три проиндексированных примера подтверждают работу индексации, но не улучшение
обнаружения замечаний. Проверка качества необходима также для поиска с замороженной
embedding-моделью: сравниваются результаты анализа и ложные срабатывания.

Для текущей проверки доступны индексация, просмотр состава и поиск в выбранной
версии, а также выгрузка фиксированного ZIP. Общий readiness Knowledge не
перечисляет динамически все назначенные коллекции по разделам; работоспособность
выбранной версии проверяется отдельно на Linux. Команды и формат отложенного
набора: [experience-index.md](experience-index.md).

## Как использовать дообученные веса

Первый эксперимент предлагается выполнять с LoRA/QLoRA и отдельным адаптером.
Базовые веса остаются замороженными; обучение создаёт небольшие матрицы поправок.
При inference базовая модель и совместимый адаптер используются вместе.
QLoRA относится к способу экономии памяти при обучении; совместимость полученного
адаптера с фактической моделью, квантованием и версией runtime проверяется отдельно.

Такой способ описан в [документации PEFT](https://huggingface.co/docs/peft/main/en/conceptual_guides/lora).
vLLM поддерживает [обслуживание LoRA-адаптеров](https://docs.vllm.ai/en/latest/features/lora/)
и перечисляет Qwen3.5 среди [архитектур с поддержкой LoRA](https://docs.vllm.ai/en/latest/models/supported_models/).
Это не проверка установленного на сервере образа vLLM: его версию,
параметры запуска, формат базовой Qwen и свободную VRAM нужно сверить перед экспериментом.

### Размер на диске и память

Размер зависит от ранга LoRA, выбранных слоёв, dtype и дополнительных сохраняемых
модулей. Число замечаний не задаёт размер адаптера.
Для одной матрицы размером `d_out × d_in` число параметров LoRA равно
`r × (d_in + d_out)`; итог суммируется по выбранным матрицам.
При FP16/BF16 сырые веса занимают примерно два байта на параметр.

Примеры расчёта, не обещание размера адаптера нашей Qwen:

| Обучаемые параметры адаптера | Сырые веса FP16/BF16 |
|---|---|
| 10 миллионов | Около 20 МБ |
| 100 миллионов | Около 200 МБ |
| 500 миллионов | Около 1 ГБ |

Полное дообучение/слияние создаёт самостоятельный checkpoint масштаба базовой
модели. Для 27 миллиардов параметров в 16 бит это примерно 54 ГБ сырых весов;
конфигурация и фактическое число параметров уточняют размер. Например, официальный
[репозиторий Qwen3.5-27B](https://huggingface.co/Qwen/Qwen3.5-27B/tree/main)
содержит около 55,6 ГБ файлов. Квантованный checkpoint имеет другой размер.

Для inference адаптеру нужна дополнительная VRAM поверх уже загруженной Qwen.
Также требуется память для рабочих буферов и KV cache. При совместимом LoRA-runtime
базовую Qwen не нужно заменять ради каждой версии адаптера; откат возвращает работу
без адаптера либо с предыдущим проверенным адаптером.

Полная модель вместо адаптера обычно требует переключения checkpoint, если GPU
не вмещает оба. Точный бюджет VRAM нельзя получить из размера файлов.
Обучение требует памяти также для активаций, градиентов и оптимизатора.
Размер изображений, контекст, batch, dtype, checkpointing и GPU определяются
экспериментом. Если GPU не хватает на обучение одновременно с production inference,
потребуется отдельный GPU/сервер или согласованное окно обучения.

vLLM обслуживает уже обученные веса. Обучение выполняет отдельный training worker,
а не HTTP-запрос анализа и не worker векторизации.

## Предлагаемое хранение будущих артефактов

В текущем проекте **нет** volume весов дообучения и действующего пути таких весов.
Следующие пути предлагаются для отдельного training service:

```text
volume: experience_training_artifacts
container mount: /data/training

/data/training/datasets/<dataset_uuid>/
  manifest.json
  examples.jsonl
  crops/

/data/training/weights/<weights_uuid>/
  adapter_config.json
  adapter_model.safetensors
  manifest.json
  training-config.json
  evaluation.json
```

У volume должен быть один владелец — training service. Experience хранит ссылки,
состав версий, SHA-256 и аудит, не бинарные веса в PostgreSQL.
Training получает фиксированный пакет данных через контракт Experience;
произвольный путь от браузера не принимается. Разделение train/validation/held-out
выполняется по SHA-256 документов, чтобы повторные прогоны одного PDF не пересекали
выборки. Отрицательные примеры требуют отдельного формата задачи и loss;
тег Bad нельзя автоматически превратить в желаемый положительный ответ модели.

Артефакт весов должен фиксировать физическую базовую модель и её ревизию,
тип адаптера/квантования, rank/target_modules, параметры обучения,
dataset UUID и manifest SHA, SHA файлов и отчёт качества.
Сейчас `model=shared-vlm` — логический серверный контракт; этого одного имени
недостаточно для воспроизводимого обучения и проверки совместимости весов.

Доступ inference к проверенным артефактам настраивается владельцем shared stack.
Существующий volume модели Qwen не перезаписывается. Путь `/data/training/...`
не означает, что этот каталог уже смонтирован в `shared-vlm`.

## Границы ответственности

| Компонент | Ответственность |
|---|---|
| Gateway | Серверная личность, разрешения, доступ к заданиям и операциям |
| Experience | Review, каталог, выбор редакций, реестр наборов/версий, аудит |
| Knowledge | Embedding, Qdrant, поиск в назначенной версии нормативного раздела |
| Будущий training service | Очередь обучения, GPU job, данные эксперимента, веса и контрольные суммы |
| Shared model deployment | Проверка совместимости, загрузка, warm-up, переключение и откат runtime |

PDRD использует логические `shared-vlm`/`shared-embedding`.
Physical model ID, GPU, TP/DP и resident runtime принадлежат shared infrastructure.
Приложение не перезапускает shared-vlm и не загружает базовую модель на каждый запрос.
Будущее применение должно различать сохранённое намерение и фактическое состояние
deployment: версия считается работающей после подтверждения загрузки и warm-up.
При частичном сбое прежняя рабочая версия остаётся назначенной; повтор операции
идемпотентен. Изменение shared stack выполняется отдельным этапом.

## Зависимость от auth/user/admin

Для проверки текущего индекса и подготовки эксперимента достаточно существующего
режима одного серверного оператора. Полноценные пользователи не заменяют
training worker, независимый проверочный набор или серверную приёмку E.

Для многопользовательского режима необходимо подключить реальные политики:

- доверенная личность на каждом запросе вместо фиксированного actor;
- владелец/область доступа документа и задания, включая миграцию старых записей;
- серверные разрешения на Review, каталог, подготовку/применение версий и нормативный CRUD;
- допуск в Experience по роли и происхождению задания; действия проектировщика
  не должны автоматически становиться инженерной обучающей разметкой;
- специальные административные операции и аудит.

Скрытие кнопки не заменяет серверную проверку. Пакетные действия обязаны проверять
права на все задания набора. Auth устанавливает личность, user — профиль/связи,
admin — управление; владельцы ресурсов и правила допуска остаются ответственностью
соответствующих сервисов и политик Gateway. CAD без исходного PDF требует
самостоятельной интеграции источника геометрии.
