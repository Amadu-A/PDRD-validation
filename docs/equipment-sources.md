# Источники оборудования и восстановление Understanding

## Управление сайтами

Раздел личного кабинета «Источники оборудования» доступен по существующему
праву `equipment_sources.manage`. Роль администратора сама по себе не заменяет
серверную проверку права. Навигация, чтение, изменение и аудит сохраняют
прежнюю авторизацию; запись проходит через Gateway с CSRF и проверенным инициатором.

| Представление | Состояние в каталоге |
|---|---|
| Используется для поиска | `trusted`, `enabled=true` |
| Не используется | `blocked` либо `enabled=false` |
| Новый сайт | `pending`, до отдельного решения |

Включение отправляет `trusted/true`, выключение — `blocked/false`.
Явный запрет действует и при `allow_unverified=true`.
Разрешение неподтверждённого источника в задании не меняет общий каталог.
Сохранённые документы и их исторический `trust_status` не переписываются.
Разрешённый сайт не доказывает применимость паспорта к конкретной модели.

Переключатель сохраняется сразу. Повторная запись той же строки блокируется
до ответа; при ошибке возвращается последнее подтверждённое состояние.
При неизвестном исходе сетевого запроса пользователь может сверить состояние
обновлением страницы. Смена сессии лишает старые обработчики права изменять UI.

Форма добавления содержит производителя и HTTPS-адрес. Основной домен и `www`
остаются разными точными hostname. `create_only=true` запрещает форме добавления
менять уже существующий источник; конфликт возвращает HTTP 409 без новой
аудит-записи. Уникальность проверяется также при одновременных запросах.

Отсутствующий `allow_http` передаётся как `None`. Репозиторий разрешает его
под блокировкой строки: сохраняет прежнее значение, для нового сайта использует
`false`. Явный флаг прежних внутренних клиентов поддерживается. Настройка HTTP
убрана из обычной формы; проверки TLS, redirect и публичного адреса загрузчика
не меняются. Новых миграций и полей БД нет.

Группы производителей, поиск и фильтры работают по ответу существующего API.
Сохраняется его действующий предел 500 записей. Инициатор и время берутся из
каталога/аудита; отсутствующее имя не заменяется выдуманным. Если API хранит
только UUID другого пользователя, он доступен в подробной истории, а основная
строка сообщает об отсутствии имени.

## Переполнение ответа страницы

Обычный успешный Understanding использует прежние prompt/schema и один
логический вызов. `VisionModelOutputBudgetError` или `finish_reason=length`
включают восстановление с тем же изображением и исходным текстом:

1. Лёгкие основные поля страницы отдельно от D и EQ.
2. При переполнении ядра — группы его полей с прежней ёмкостью.
3. Факты D порциями до четырёх, идентификации EQ — до восьми.
4. При новом переполнении ёмкость соответствующей порции уменьшается вдвое.
   Ошибка единичной записи остаётся явной ошибкой; слепого повтора нет.

Продолжение исключает уже полученные точные записи. Общие прежние пределы D
и EQ сохраняются. Выключенная возможность не вызывает извлечение её данных.
Детерминированные строки спецификации и grounding производителя остаются
в прежнем сценарии. Обрезанный JSON не используется. Отмена проверяется перед
каждой новой порцией; метрики включают неудачные и успешные обращения.

Страница 20 исходного «ИОС 4.1.7» проверена с D+EQ на настоящем shared-vlm
без кеша: исходное переполнение 6400 воспроизвелось, восстановление завершилось,
сохранены 12 фактов D. Отдельно проверена принудительная ветка восстановления.
Это не подтверждает полный анализ 31 страницы со всеми внешними источниками.

## Полный проход ТЗ

Предел полного входного списка повышен до 2000 в настройках Analysis и трёх
workflow. Пагинация Knowledge допускает 10 страниц по 200; проверка полноты,
принадлежности и уникальности ID сохранена. Превышение предела явно отклоняется,
требования не усекаются. VLM-порция остаётся 48: 1094 требования дают 23 вызова
на лист, включая последнюю порцию из 38. ТЗ по-прежнему необязательно.

`.env.example` содержит новый предел. Если в `.env` уже есть явное значение
`ANALYSIS_SERVICE_PIPELINE__TECHNICAL_ASSIGNMENT_MAX_REQUIREMENTS_PER_PAGE`, оно
имеет приоритет. Для увеличения лимита нужно изменить существующее переопределение
или удалить его, оставив baseline; новую строку добавлять не требуется.
После обновления необходимы пересборка Analysis и публикация изменённых workflow
в n8n. Изменения n8n относятся к исправлению T-first, а не к интерфейсу каталога.

Регрессия на 1094 требования проверяет все ID, порядок и размер каждой порции.
Настоящий прогон всех этих требований на GPU и большой EQ-спецификации с внешним
поиском требует отдельной серверной приёмки.
