# Личный кабинет PDRD: проект интерфейса

Этот документ задаёт экран личного кабинета для этапа Identity. [Автономный
макет](previews/personal-account.html) показывает пять состояний без подключения
к сервисам и без настоящих персональных данных. Макет не входит в production
frontend; кнопки в нём не выполняют вход, выход или анализ.

## Место в приложении

Личный кабинет станет отдельной страницей `/account.html` существующего
frontend. Это не четвёртый микросервис. Общая навигация ведёт к анализу, личному
кабинету и, при соответствующем праве, к отдельной админке. Браузер обращается
только к публичному API Gateway по HTTPS. `user-service` остаётся владельцем
профиля и разрешений, `auth-service` — входа и серверных сессий,
`admin-service` — административных сценариев. Браузер не вызывает
`/internal/v1/*`, не получает межсервисный ключ и не задаёт себе роль.

Сейчас `user-service` предоставляет только внутренние маршруты. Публичных
проверенных сессий и `/api/v1/users/me` ещё нет, поэтому включать реальный
кабинет в production frontend преждевременно. Данные на макете — примеры.

## Состояния и содержание

| Состояние | Что показывает кабинет | Доступ к работе |
| --- | --- | --- |
| Гость | Возможность войти или зарегистрироваться, условия временной выдачи результата | Загрузка PDF/CAD/ТЗ/ПЗ, анализ, скачивание автозамечаний по временной случайной ссылке |
| Внешний аккаунт с подтверждённым email, бесплатный уровень | Имя, email, статус подтверждения, управление будущей сессией | Тот же бесплатный анализ, что у гостя; оплата или наличие аккаунта сами по себе не дают рабочую роль |
| Проектировщик | Профиль, назначенная роль, собственные рабочие возможности | Анализ, свои документы и Review, добавление Gold; без принятия/отклонения и утверждения замечаний |
| Руководитель | Профиль, роль и область ответственности | Решения по Review и явное утверждение, после которого допускается внесение проверенного результата в Experience; нормативные операции в разрешённой области |
| Администратор | Профиль и переход к отдельной админке | Только предусмотренные административные операции, а не произвольный доступ к SQL |

Для гостя и бесплатного внешнего аккаунта блок пользовательской документации
неактивен, редактирование нормативки запрещено, системный промпт скрыт,
ручное Review и сохранение замечаний в базу недоступны. Полученные
автозамечания не становятся объектами Review/Experience. Временная ссылка на
результат ограничена по сроку и хранится по серверной политике; постоянную
«историю анализов» до реализации принадлежности данных не показываем.

Основная страница кабинета содержит обзор доступа, профиль, блок безопасности
и список разрешённых действий. Поля корпоративного профиля, полученные из AD,
показываются только для чтения; формы изменения пароля AD в PDRD нет. Отдел и
организация появятся после безопасного публичного контракта членства; текущий
внутренний `UserResponse` их не возвращает. Список устройств, выход из одной
или всех сессий и настройка «Запомнить меня» становятся действиями только
после готовности серверных маршрутов `auth-service` и CSRF-защиты. Платёжные
элементы и фиктивные тарифы в первой версии кабинета не нужны.

## Контракты и защита

Планируемые публичные маршруты через Gateway:

| Маршрут | Назначение |
| --- | --- |
| `GET /api/v1/auth/session` | Проверка действующей серверной сессии и её срока без передачи токена JavaScript |
| `GET /api/v1/users/me` | Безопасный профиль текущего пользователя и вычисленные сервером UI-возможности |
| `GET /api/v1/auth/sessions` | Список собственных устройств после появления session storage |
| `POST /api/v1/auth/logout`, `POST /api/v1/auth/logout-all` | Завершение сессий с CSRF-защитой |

Это **проект контрактов**, а не перечень уже реализованных маршрутов.
`/api/v1/users/me` должен собирать профиль и права только по доверенной
сессии. Набор `capabilities` может помогать показывать интерфейс, но каждый
запрос на анализ, документы, Review, нормативку и Experience требует
самостоятельной серверной проверки операции и доступа к конкретному объекту.
Служебный ключ Review в существующем Nginx не является идентичностью
пользователя. Нельзя строить новую авторизацию на наличии этого заголовка.

При `401` кабинет показывает гостевое состояние. При `403` или заблокированном
профиле показывает явное сообщение о недоступности; при сетевой ошибке или
`5xx` — ошибку связи и повторную попытку. Эти ситуации нельзя смешивать с
обычным гостем. Загрузка скрывает персональные данные предыдущей сессии.
Смена роли или блокировка инвалидации полномочий требует серверной проверки
`authorization_version`, независимо от того, что уже нарисовано в браузере.

## Порядок реализации и проверки

1. Завершить `auth-service`: корпоративный вход через защищённое LDAP-соединение
   после получения параметров от IT, внешнюю регистрацию с подтверждением
   email, непрозрачные серверные сессии, выход и отзыв сессий. Пароль AD в PDRD
   не хранить.
2. Добавить Gateway principal и публичные безопасные контракты профиля,
   полномочий и сессий. Проверить действия гостя, бесплатного пользователя и
   рабочих ролей на стороне сервера, включая прямые запросы к API.
3. Создать `/account.html` в production frontend с отдельными BEM-блоками,
   модульным JavaScript и общим `style.css`. Заменить примерные данные живыми
   ответами Gateway, обеспечить загрузку, `401`, `403`, ошибку связи и истечение
   сессии. Для AD-полей использовать режим только для чтения.
4. Добавить unit, функциональные, интеграционные, архитектурные и необходимые
   нагрузочные проверки для серверных операций; frontend тесты состояний,
   ошибок и действий. Визуально сравнить desktop и mobile, проверить работу
   клавиатурой, фокус, контраст и имена элементов управления.

Для текущего визуального ревью откройте
`docs/previews/personal-account.html` в браузере. Переключите пять состояний,
проверьте ширину окна около 1280 px и 390 px, а также выбор радиокнопок
клавиатурой. Видимое предупреждение на макете должно сохраняться во всех
состояниях: это проект экрана, а не действующая сессия или разрешение.
