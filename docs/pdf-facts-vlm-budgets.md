# Единые факты PDF и бюджеты VLM

## Что изменено

`equipment_specification` остаётся существующим источником данных таблицы.
Document Service читает исходные строки один раз. Analysis Service формирует из
них сведения листа (`PageFacts`), оборудование EQ и обычные `DocumentFact` для D.
Новые DTO, таблицы БД или отдельный pipeline не вводятся.

| D: контекст всего PDF | EQ: поиск оборудования | Извлечение спецификации | Факты D | Записи EQ |
| --- | --- | --- | --- | --- |
| Выключен | Выключен | Нет | Нет | Нет |
| Включён | Выключен | Да | Да | Нет |
| Выключен | Включён | Да | Нет | Да |
| Включён | Включён | Да | Да | Да |

Эти флаги независимы. Разрешение неподтверждённых интернет-источников относится
к EQ и не управляет извлечением таблиц или включением D. N, T, U и E используют
прежние этапы. Нормативные запросы для программной таблицы строит следующий
существующий `BuildNormativeQueries`; сама таблица не выдумывает нормативные основания.

## Выбор маршрута

Document Service дополняет тот же контракт полем `page_content`, версия 1:
области таблиц, текст вне таблиц, счётчики нетабличной графики и изображений,
`requires_vision`, фиксированный код причины и маршрут.

- **pdf_table**: надёжная текстовая спецификация с полным контролем строк,
  без необъяснённой графики, изображений и плотного текста вне таблицы.
  Базовые сведения, D и EQ формируются программно. Основного VLM-вызова нет.
- **mixed**: надёжная таблица соседствует со схемой, изображением или сложным
  текстом. Таблица читается программно; прежний Understanding получает изображение,
  текст вне таблицы и инструкцию извлекать только нетабличные сведения.
- **vision**: скан, отсутствие таблицы или неполный/ненадёжный результат.
  Сохраняется визуальная обработка; основной Understanding делает не более одного
  логического запроса на лист. Восстановительных VLM-вызовов после переполнения нет.

Отсутствующие или неподдерживаемые метаданные не доказывают чистый табличный маршрут.
Ошибка анализа геометрии также требует VLM. Изображение внутри таблицы требует
визуальной проверки. Изображения штампа исключаются только при подтверждённых
подписях штампа. Область таблицы строится по содержательным строкам, поскольку
`find_tables()` иногда объединяет таблицу со всей рамкой и штампом листа.

Для спорных позиций сохраняется существующее короткое текстовое уточнение:
до 20 строк, около 6000 символов, 2400 токенов, максимум четыре обращения на лист.
Исчерпание лимита или отказ модели оставляют исходную позицию с `needs_review`.
Отмена и общий limiter сохраняют существующие контрольные точки и порядок страниц.

## Происхождение фактов и сравнение

Все подтверждённые значения сохраняются без ограничения VLM `max_facts_per_page=12`.
Этот лимит применяется к генерируемым нетабличным фактам. Из отдельных исходных
столбцов читаются наименование, изготовитель, модель, исполнение, артикул,
количество и единица. `Caption` остаётся экспортным представлением и не разбирается.
Числа марки не превращаются в технические параметры; неоднозначная модель не
становится подтверждённым значением D.

Каждый программный факт сохраняет:

- `source_item_id`, `source_row_ids`, `source_pages`, все `source_regions`;
- исходное значение, единицу и текст доказательства;
- номер позиции, таблицу, столбец, группу и режим/роль подтверждённого параметра;
- `extraction_method=pdf_table` и визуальные области текущей физической страницы.

Идентичность и `scope_segment` задаются `item_id`. Две позиции одной модели с
разным количеством остаются разными проектными объектами. Одинаковый факт одной
строки не становится двумя независимыми доказательствами. В смешанной ветке копия
таблицы от VLM исключается по ID исходной позиции или полному покрытию её областей
известной таблицей. Факт схемы вне таблицы сохраняется. Неизвестное происхождение
не позволяет удалять факт только по похожему тексту.

Передача через HTTP и n8n сохраняет все факты и их происхождение. D-контекст
по-прежнему ограничивает выдачу источников для конкретной проверки; внутренний
поиск связанной таблицы больше не создаёт квадратичные повторные списки фактов.

## Бюджеты и ошибки

Перед экспериментом на aistation подтверждены: две попытки, retry 14000,
Understanding 3200, финализация 4000, T-first: лимит 2000 и порция 48.
`/v1/models` работающего `shared-vlm` сообщил `max_model_len=262144`.
Снимок пользователя: четыре A100-SXM4-80GB, 81920 MiB каждая, загрузка 0%.
Это снимок простоя; распределённая нагрузка и запас GPU под параллельные проекты
этим измерением не подтверждаются. Физическая конфигурация остаётся в shared-infrastructure.

Новые значения согласованы в Python и `.env.example`:

| Настройка | Значение |
| --- | --- |
| Максимум попыток адаптера | 3 |
| Верхний бюджет адаптивного ответа | 16000 |
| Начальный Understanding | 4000 |
| Начальная финализация | 6000 |
| Начальная проверка N | 14000, сохранён |
| Начальная проверка T | 4000, сохранён |
| Требований T на страницу / порция | 2000 / 48, сохранены |
| Локализация / уточнение спецификации | 4000 / 2400, сохранены |

При известном размере контекста увеличение ответа дополнительно ограничено
`max_model_len - prompt_tokens - 512`, с резервом под повторный промпт. Повтор с
тем же исчерпанным бюджетом запрещён. С 15.10.2026 общий Understanding больше
не восстанавливается отдельными VLM-запросами после `length`: сохраняются программные
данные, визуальные сведения остаются пустыми, Check Norms получает исходные текст
и изображение. Низкоуровневые повторы адаптера не менялись. Политика других этапов
остаётся прежней. Подробности и контрольный прогон: [understanding-no-recovery.md](understanding-no-recovery.md).

Финализация распознаёт `VisionModelOutputBudgetError` без зависимости от старых
текстов Ollama и делит не поместившуюся порцию. Синтаксически корректный JSON с
`finish_reason=length` также считается неполным. Исходные ID и защищённые кандидаты
сохраняются. Если не помещается один кандидат, ошибка остаётся явной: HTTP 503 с
JSON, вместо ложного успешного результата. Обычные правила отбора неподтверждённых
замечаний и fallback для пропущенной моделью записи сохраняются.

`.env` автоматически не изменяется. Compose загружает сначала `.env.example`,
затем `.env`; старые явные переопределения этих четырёх настроек имеют приоритет.
Для принятия новых defaults удалите только соответствующие старые переопределения
после проверки своих настроек или осознанно установите необходимые значения.

## Диагностика

Журнал `understanding_page` и HTTP `metrics.understanding` содержат номер страницы,
флаги D/EQ, маршрут, статус/полноту спецификации, количество строк и позиций,
программные/генерируемые факты, число HTTP-попыток адаптера, cache hits, восстановлений,
входные/выходные токены, длительность и фиксированный код причины. `job` содержит
внутренний `document_id`, чтобы отделять параллельные задания. `recovery_count` считает
восстановительные запросы (теперь 0), `output_budget_count` — переполнения;
`main_request_count` — логические основные запросы, включая обращения к кешу.
`result=incomplete` и `limited_reason=output_budget` явно обозначают ограниченный результат.

Стоимость суммируется по всем полученным ответам, включая неудачные JSON/length
попытки и уточнения. Cache hit не считается GPU-запросом. Когда
usage не получен, значение `null` означает неизвестный расход, а не ноль.
Сетевые повторы учитываются как HTTP-попытки; это не доказательство выполненного
inference. Полные промпты, исходные страницы и ответы модели в диагностический
журнал не записываются. Ошибки API также не включают тело ответа провайдера.

## Историческое измерение настоящего PDF 14.10.2026

Следующие числа относятся к реализации с recovery. Они не доказывают скорость
исправления от 15.10.2026; оно требует отдельного полного прогона того же документа.

Контрольный файл: `tests/fixtures/equipment/ios-4-1-7.pdf`, SHA-256
`9ccabd0f34f2950ad0c2dd8752b351ffe54ab6b8455ddc4b7887f402733022f0`.
Оба прогона использовали настоящий PDF reader, HTTP Understanding stage и shared-vlm,
D и EQ включены, кеш отключён, максимум один одновременный запрос.

| Показатель | До | После |
| --- | --- | --- |
| Страницы / HTTP | 31 / 200 | 31 / 200 |
| Исходные строки / позиции | 255 / 131 | 255 / 131 |
| Контроль полноты | Пройден | Пройден |
| Основной Understanding на листах 24–31 | Требовался | 0 вызовов |
| Программные факты D | 0 | 515 |
| Обращения к порту модели | 43 | 76 |
| Фактические HTTP-попытки по START/DONE | 69 | 76 |
| Входные токены всех попыток | 364947 | 402446 |
| Выходные токены всех попыток | 218557 | 135021 |
| Время stage | 1862,59 с | 1160,37 с |
| Переполненные обращения, затем восстановленные | 2 | 10 |

Число HTTP-попыток выросло примерно на 10%, входных токенов — на 10%.
Выходных токенов стало на 38% меньше, время сократилось на 38%.
Это результат совместного изменения источника фактов, бюджета и раннего разбиения;
отдельный вклад каждого изменения не измерялся. Листы со схемами потребовали
больше коротких обращений. Нельзя называть этот результат уменьшением общего
числа запросов. Финальный JSON обеих проверок сохраняет все 255 строк и 131 позицию.

В исходном старом `summary.json` сумма попыток равна 65: туда не попали четыре
неудачные попытки двух окончательно переполненных обращений. Для сравнения
использованы все 69 START/DONE из полного журнала; новая реализация учитывает их сразу.

Отдельный протокольный GPU-прогон финализации с бюджетом 6000: десять явно тестовых
кандидатов без оснований, один запрос, HTTP 200, 3108 входных и 1175 выходных токенов,
9,00 с. Правила отбора отклонили все десять неподтверждённых кандидатов. Этот smoke
проверяет запрос и бюджет, но не заменяет приёмку реальных замечаний проекта.

Проверено автоматически: реальный PDF с комбинациями D/EQ, смешанный лист,
изображение внутри/вне таблицы, скан/ненадёжный контракт, сохранение происхождения,
раздельные позиции, дедупликация, bounded memory D, HTTP, настоящий код выражений
n8n, typed split финализации, неизвестный usage и реальный файловый cache hit.

**Пока не подтверждено:** полный анализ через опубликованный n8n, настоящий
T-first всех 31 страниц с реальным набором 1094 требований, нагрузка с внешним
поиском большого EQ. Для T-first нужен сам набор требований/документ ТЗ, а для
сверки runtime workflow — экспорт опубликованной версии. Лимит 2000 и порция 48
подтверждены серверными Settings; файл workflow в репозитории также содержит 2000.
Синтетические проверки 1094 ID не выдаются за настоящий GPU-прогон ТЗ.

## Повторение и обновление

Сначала обычная полная Windows-проверка `ops/check-quality.ps1` и просмотр diff.
Полный журнал сохраняйте вне репозитория, например в `$env:TEMP`.
Индексируйте только пути из приложенного staging-скрипта; commit/push выполняет пользователь.

На сервере, без активных анализов:

`origin` сервера должен указывать на приватный `neo-term-it/PDRD-validation`.
Fetch создаёт ссылку новой ветки перед её переключением.

```bash
set -euo pipefail
cd ~/projects/PDRD-validation
git fetch origin feature/quality
git switch feature/quality
git pull --ff-only origin feature/quality
bash ops/check-quality.sh > /tmp/pdrd-pdf-facts-quality.log 2>&1
```

Проверьте код завершения gate до пересборки. После успешного gate:

```bash
docker compose build document-service analysis-service > /tmp/pdrd-pdf-facts-build.log 2>&1
docker compose up -d --no-deps document-service analysis-service > /tmp/pdrd-pdf-facts-up.log 2>&1
docker compose exec -T analysis-service python -c 'from pdrd_analysis_service.core.settings import Settings; s=Settings(); print("attempts:",s.vlm.max_attempts,"retry:",s.vlm.max_retry_num_predict,"page:",s.pipeline.page_facts_num_predict,"final:",s.pipeline.final_num_predict,"T limit:",s.pipeline.technical_assignment_max_requirements_per_page,"T batch:",s.pipeline.technical_assignment_batch_size)'
curl -fsS --max-time 10 http://127.0.0.1:8301/health/ready
curl -fsS --max-time 10 http://127.0.0.1:8501/health/ready
```

Миграций в этом исправлении нет. Импортируйте и опубликуйте только изменённый
`n8n/workflows/analysis-v2-pdf.json` через принятую процедуру n8n. В узле
Document Extract PDF поле `include_equipment_specification` должно включаться
при D **или** EQ. Проверьте опубликованную версию, а не только редактор.

Автономный контроль Understanding в среде с зависимостями обоих сервисов:

```bash
python scripts/check_specification_vlm.py \
  --base-url http://shared-vlm:8000/v1 \
  --document-context --require-programmatic-tables \
  --page-num-predict 4000 --max-attempts 3 --max-retry-num-predict 16000 \
  --output-dir /tmp/pdrd-pdf-facts-gpu-new
```

Это не команда для контейнера Analysis с отсутствующим Document Service source.
Прогон требует установленных зависимостей обоих сервисов и адреса runtime,
доступного из выбранной среды. Каждый запуск сохраняйте в отдельный каталог.

В файлах результата остаются полные ответы и метрики, в консоли — только итог.

## Что проверить руками

1. Через рабочий внутренний HTTPS-адрес открыть frontend, убедиться в загрузке JS/CSS,
   выбрать PDF ИОС 4.1.7, страницы 1–31, включить D и EQ. Основные этапы должны
   закончиться без ошибки страницы 20 или 25 и без сообщения о невалидном JSON n8n.
2. В результате сверить 255 строк, 131 позицию, страницы 24–31 и полноту спецификации.
   В журнале `understanding_page` для этих восьми страниц ожидать `pdf_table`,
   положительные `programmatic_facts`, отсутствие основного `page_understanding`.
   Короткие уточнения спорных строк возможны.
3. Повторить D включён / EQ выключен: D должен получить исходные факты таблиц,
   интернет-задание EQ не создаётся. Затем EQ включён / D выключен: перечень EQ
   сохраняется, межстраничная D-проверка не запускается.
4. Проверить скан и смешанный лист: схема/изображение остаются в визуальном анализе.
   Разные проектные позиции одной модели и их количества остаются раздельными.
5. Проверить действующий проект с настоящим ТЗ 1094: опубликованный Requirement Feed
   не должен ограничивать его 1000 записями. Сохранить все переданные requirement_id,
   полный итог T-first и токены/время всех 31 страниц; равенство набора ID проверять
   по сохранённому результату, а не по числу замечаний.
6. Проверить реальные замечания после финализации: IDs/основания/привязки сохранены,
   защищённые D/EQ-кандидаты не теряются, отмена не начинает следующую порцию.
   Частичный внешний поиск документации может дать неполный EQ независимо от D.
