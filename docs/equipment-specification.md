# Извлечение оборудования из PDF-спецификаций

## Назначение

При включённом поиске оборудования в интернете (EQ) или контексте PDF (D) Document Service сначала
проверяет заголовки текстового слоя страницы. Таблицы спецификации извлекаются
через PyMuPDF до обращения к VLM. Производитель берётся из столбца изготовителя,
модель — из столбца марки, количество и единица — из своих столбцов.
Предположение модели о производителе не становится исходными данными таблицы.

Надёжная чистая текстовая таблица формирует базовые `PageFacts`, EQ и факты D
из одних исходных строк, без основного page-understanding вызова VLM. На смешанном
листе VLM проверяет только нетабличные сведения. Нормативный поиск N, техническое задание T,
пользовательские пакеты U, опыт E, Review и поиск паспортов используют прежние этапы.
Если D и EQ выключены, дополнительное извлечение таблиц не запускается.
Правила маршрутизации, бюджеты и измерения новой реализации описаны в
[Единых фактах PDF](pdf-facts-vlm-budgets.md). Результаты ниже от 13.10.2026 относятся
к предыдущей реализации.

У скана без текста и страницы без надёжно распознанной таблицы сохраняется прежний
визуальный маршрут. Ошибка `find_tables()` сохраняет текст, изображение и явное
предупреждение о необходимости визуального извлечения. Частичный результат
остаётся в отчёте; его нельзя выдавать за полную спецификацию.

## Структура и сохранение строк

Каждая обнаруженная строка таблицы, включая заголовки, подписи групп и штамп,
хранится в `raw_rows`: исходные ячейки, физическая страница, номер таблицы,
уникальный `row_id` и область в координатах 0–1000. Значение `None` объединённой
ячейки сохраняется и отличается от явно пустой ячейки. Ограничения в 40 строк нет.

Внутри страницы продолжение объединяется только при подтверждённом rowspan
позиции и отсутствии самостоятельных марки, изготовителя, количества и единицы.
Изделие без позиции, но со своим количеством, остаётся отдельной записью с
`needs_review`. Исходные ячейки не удаляются даже после объединения.

Между соседними выбранными страницами объединение требует одинакового непустого
шифра проекта, номера позиции и явной пометы «Продолжение позиции …».
Конфликт модели, изготовителя, единицы или количества запрещает объединение.
Цепочка из трёх страниц также сохраняет все `row_id`, страницы и области.
Неоднозначные границы остаются отдельными позициями. Группа `Under` наследуется
только от явной подписи в той же спецификации, а не из предположения о назначении изделия.

Python сопоставляет исходные строки с позициями. Analysis Service независимо
проверяет количество, уникальность ID, полноту, типы полей и геометрию; повреждённый
контракт получает HTTP 422 до запуска GPU. Итоговый отчёт дополнительно проверяет
межстраничное владение строками.

Для неоднозначных строк разрешено короткое текстовое уточнение через существующий
порт модели, общий кеш и GPU limiter. Порция содержит до 20 строк и примерно
6000 символов исходных полей, без изображений. Максимум — четыре вызова на страницу,
`num_predict=2400`. Крупная строка или исчерпанный лимит остаются в результате.
Состав строк и исходные поля защищены от изменения: заполнить пустое поле можно
только по явной подписи в собственной исходной ячейке. Недоступность уточнения,
выдуманное значение или изменение состава ответа не удаляют позиции.
Отмена проверяется между порциями и перед последующим основным VLM-вызовом.

Характеристики читаются из наименования, не из собранного Caption или цифр модели.
Тепловая мощность хранится отдельно от электрической; единицы не восстанавливаются
из обозначений `Ру16`, `Ду200` или `РИП-12`. Неподдерживаемая для сравнения
характеристика остаётся исходным текстом и не становится подтверждённым нарушением.

## Результат

Document HTTP принимает optional multipart-поле
`include_equipment_specification=false`. При включении страница получает
`equipment_specification`. Это же optional-поле передаётся в Understanding.

Итог PDF-workflow содержит `equipment_check.specification`. Основной формат:

```json
{
  "items": [
    {
      "Caption": "Кран шаровой фланцевый, класс А, Н/П, Ду200, Ру16, под установку редуктора; КШ.Ц.Ф.Р200/150.016.Н/П.02; ЧСГС",
      "Units": "шт.",
      "Quantity": "6",
      "UserComment1": "120/155-16-ИОС4.1.7",
      "Under": "Котловой контур"
    }
  ]
}
```

В соседних полях отчёта сохраняются `structured_items`, `raw_rows`,
`raw_row_count`, `item_count`, `pages`, `coverage_complete` и предупреждения.
Структурированная позиция содержит отдельно наименование, модель, изготовителя,
исполнение, артикул, количество, единицу, шифр, группу, характеристики,
исходные ячейки, `row_ids`, `source_pages` и `source_regions`.

EQ Search получает уникальные модель/исполнение/артикул с сохранением строгого
производителя. Повторяющиеся позиции остаются отдельными вхождениями в inventory;
каждое имеет количество, единицу и ссылки на исходные строки. Количество строк
спецификации, число уникальных моделей и число физических вхождений — разные
показатели. Отсутствующая марка не угадывается из наименования.

PDF-workflow изменён только для передачи трёх данных: флага извлечения в Document,
спецификации в Understanding и результата спецификации в `equipment_check`.
Текущий HTTP body перечисляет поля явно, поэтому без этой правки он терял бы
новый контракт. После обновления требуется импортировать и опубликовать
`n8n/workflows/analysis-v2-pdf.json`; остальные workflows не меняются.

## Контрольный документ и результаты

Fixture: `tests/fixtures/equipment/ios-4-1-7.pdf`, 31 физическая страница.
SHA-256: `9ccabd0f34f2950ad0c2dd8752b351ffe54ab6b8455ddc4b7887f402733022f0`.
Восемь страниц 24–31 содержат 255 исходных строк, 129 пронумерованных позиций
и две отдельные гильзы без номера: всего 131 позиция. Штампы и заголовки не
считаются оборудованием, но сохраняются в исходных строках.

Реальный прогон 13.10.2026 через production PDF reader и HTTP Understanding stage
на `shared-vlm`, без кеша, с EQ и выключенным D:

| --- | --- |
| Страницы 1–31 | HTTP 200, все страницы в исходном порядке |
| Страницы спецификации | 24–31; повторный массив оборудования не запрошен |
| Исходные строки / позиции | 255 / 131; контроль полноты пройден |

| Продолжительность stage | 275,65 с |
| Страница 25 | первая попытка, 741 output token при бюджете 3200 |
| Неопределённые гильзы | обе сохранены; неподтверждённые уточнения отклонены |

Дополнительный реальный прогон страницы 25 с D: HTTP 200, 22 позиции,
39 исходных строк. Основной ответ использовал существующий адаптивный повтор
3200 → 6400 и завершился с 5272 output tokens. Вторая попытка имеет больший
бюджет; повтор с тем же исчерпанным бюджетом не вводился.

Полная Windows-проверка: Ruff и форматирование прошли;
2317 pytest passed / 110 skipped; 291 frontend passed / 0 failed.
Пропуски относятся к наборам с внешними зависимостями: серверный quality gate
с реальными PostgreSQL/Qdrant остаётся отдельной обязательной проверкой.
GPU-прогон проверяет Understanding, а не всю опубликованную цепочку n8n,
внешний поиск паспортов или нагрузку 300/500 моделей.

## Повторение реального прогона

В среде с установленными зависимостями проекта:

```bash
python scripts/check_specification_vlm.py \
  --base-url http://shared-vlm:8000/v1 \
  --output-dir /tmp/pdrd-specification-vlm
```

Для отдельной страницы с D добавляются `--pages 25 --document-context`.
Скрипт использует реальные `PyMuPdfReader`, VLM adapter, общий limiter и HTTP
stage, отключает кеш и ограничивает одновременные GPU-запросы одним.
Он не меняет `.env` и не обращается к рабочей очереди заданий.

В каталоге результата: `summary.json`, `progress.json`, `stage-response.json`,
`specification.json`, `vlm.log`; при ошибке — `failure.json`.
Консоль содержит только итог. Все исходные данные и метрики остаются локально.
Повторный запуск делайте в отдельный временный каталог, чтобы сохранить предыдущие логи.

## Приёмка после обновления

1. При отсутствии активных анализов пересобрать только `document-service` и
   `analysis-service`, затем импортировать и опубликовать обновлённый PDF-workflow.
2. Запустить новый анализ контрольного PDF, страницы `1-31`, EQ включён.
   Understanding должен пройти страницу 25 и закончить все 31 страницы.
3. В итоговом JSON проверить `equipment_check.specification`: `item_count=131`,
   `raw_row_count=255`, страницы 24–31, `coverage_complete=true`.
4. Проверить позицию `3.8.1-3.8.6`, изготовителя ЧСГС, точную марку, количество 6,
   единицу `шт.` и наименование с окончанием «под установку редуктора».
5. Обе гильзы без номера должны остаться отдельными, с количеством 2 и признаком
   уточнения; производитель или позиция не должны подставляться из догадки.
6. Сверить уникальные входы `Build Equipment Search Inputs` с повторяющимися
   позициями inventory; недостаток паспортов может дать частичный EQ-результат,
   сохраняя весь перечень спецификации.
7. Проверить запуск с D, запуск без EQ и обычный скан; остальные источники и
   Review должны продолжать работать. При отмене следующие порции не запускаются.

Интерфейс использует существующую таблицу моделей EQ. Полный перечень позиций
с исходными ячейками доступен в JSON результата; отдельная таблица экспорта
спецификации в интерфейс в этой задаче не добавлялась.
