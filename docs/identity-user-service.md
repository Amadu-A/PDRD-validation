# User Service: границы и запуск

`user-service` хранит профиль PDRD, устойчивые внешние идентичности,
организации, отделы, членство и назначения ролей. Он не принимает пароль AD,
не хранит пароль или его хеш и не создаёт браузерную сессию. Вход сотрудников
через локальный Active Directory и регистрация внешних пользователей относятся
к следующему этапу `auth-service`.

## Данные и полномочия

- Сервис владеет только схемой PostgreSQL `users` и собственной цепочкой Alembic.
  Чужие таблицы он не изменяет.
- Связка с источником входа ищется только по
  `(provider_id, namespace, subject)`. Изменение логина или email не меняет
  владельца профиля и не объединяет два аккаунта.
- Назначения ролей пока действуют только при `role_source=local`.
  `role_source=ad_group` оставлен в модели для будущего подтверждённого
  сопоставления групп и сейчас не даёт прав.
- Версия полномочий изменяется в той же транзакции, что назначение или отзыв
  роли. Сервис учитывает действующие членства при расчёте ролей; вызывающий
  сервис отдельно проверяет право на конкретный ресурс и его область.
- Выключение организации или отдела сразу исключает членство из нового снимка
  прав. Для будущих административных операций изменения состава организации
  потребуется одновременно обновлять версии прав затронутых пользователей
  либо принудительно сбрасывать кэш полномочий и сессии.
- Роль `platform_admin` не выдаётся общим маршрутом назначения. Первое
  назначение возможно только однократной командой bootstrap после создания
  подтверждённого корпоративного профиля.

## Сетевой контур

Compose-профиль `identity` включает миграцию и сам сервис. В контейнере
`user-service` слушает порт 8000 только в сети приложения; host-порт ему не
публикуется. Маршруты `/internal/v1/*` требуют
`Authorization: Bearer <USER_SERVICE_INTERNAL_KEY>`. Ключ хранится в `.env`,
а не в `.env.example` или браузере. Маршруты изменения ролей дополнительно
получают `X-PDRD-Actor-Id` от доверенного вызывающего сервиса и **сами**
проверяют действующую роль администратора в базе. Значение роли из HTTP
запроса не считается доказательством полномочий.

До подключения `auth-service`, Gateway и пользовательских сессий этот профиль
не открывает вход и администрирование через браузер. Гостевой анализ и
действующий основной стек остаются отдельным контуром.

## Внутренний контракт

| Операция | Назначение |
| --- | --- |
| `GET /health/live`, `GET /health/ready` | Состояние процесса и PostgreSQL |
| `POST /internal/v1/identities/resolve` | Поиск профиля по устойчивому ключу |
| `POST /internal/v1/users` | Идемпотентное создание профиля с идентичностью |
| `GET /internal/v1/users/{user_id}` | Профиль для доверенного сервиса |
| `GET /internal/v1/users/{user_id}/permissions` | Текущие права и версия |
| `POST /internal/v1/users/{user_id}/roles` | Локальное назначение роли администратором |
| `DELETE /internal/v1/users/{user_id}/roles/{assignment_id}` | Отзыв роли администратором |

Публичные `/api/v1/users/*` появятся только вместе с проверкой браузерной
сессии и объектного доступа в Gateway. Прямой вызов внутренних маршрутов
браузером не предусмотрен.

Повторный `POST /internal/v1/users` возвращает уже существующий профиль, в том
числе заблокированный. Будущий `auth-service` перед созданием сессии обязан
проверить `status` и не считать успешный ответ на создание разрешением входа.

## Настройки и проверки

Значения `USER_SERVICE_DATABASE__*` и выключенный по умолчанию
`USER_SERVICE_ENABLED=false` перечислены в `.env.example`. Для явного запуска
добавьте `identity` к уже выбранным профилям в закрытом `.env` и задайте ключ.
Пример при действующем профиле `review`:

```dotenv
COMPOSE_PROFILES=review,identity
USER_SERVICE_INTERNAL_KEY=<случайный секрет не короче 32 символов>
```

Compose передаёт сервису пароль действующего проектного PostgreSQL из
`PDRD_POSTGRES_PASSWORD`. `bash scripts/up.sh` применяет миграцию схемы `users`
через зависимость Compose и ждёт внутренней готовности сервиса;
`bash scripts/check-stack.sh` проверяет миграцию и сервис только при выбранном
профиле. Обычный запуск PDRD не меняет состав контейнеров.

Для PostgreSQL-интеграции есть отдельная конфигурация
`ops/compose.user-test.yaml`: временная БД размещается в `tmpfs`, сеть
внутренняя, рабочие volumes и секреты не используются. После появления
Docker-демона тесты запускаются так:

```bash
docker compose -f ops/compose.user-test.yaml up \
    --build --abort-on-container-exit --exit-code-from user-test-runner
docker compose -f ops/compose.user-test.yaml down
```

Первого администратора после подтверждённого корпоративного входа назначают
внутри сервера командой `python -m pdrd_user_service.bootstrap_admin --user-id
<UUID>`. Она не опубликована как HTTP-маршрут и срабатывает один раз.
