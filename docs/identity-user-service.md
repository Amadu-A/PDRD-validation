# User Service: профили, роли и область доступа

`user-service` владеет схемой PostgreSQL `users`: профилями, внешними
идентичностями, организациями, отделами, членством и назначениями ролей.
Корпоративный пароль и его хеш здесь не хранятся. `auth-service` подтверждает
личность и управляет сессиями; `admin-service` вызывает разрешённые операции
`user-service` и не изменяет его таблицы напрямую.

## Роли и членство

Первая рабочая модель использует локальные роли `designer`, `department_head`
и `platform_admin`. `role_source=ad_group` оставлен для будущего сопоставления
с подтверждёнными группами AD, но сейчас не выдаёт прав. `platform_admin`
назначается только защищённой однократной bootstrap-командой. Административный
HTTP-маршрут не может выдать эту роль.

Назначение роли руководителя требует действующего членства в организации и
отделе. Изменение членства и роли использует ожидаемую
`authorization_version` (CAS), чтобы параллельные правки не перезаписали друг
друга. Версия меняется в той же транзакции. Проверка области Review допускает
руководителя к работе проектировщика только при действующем общем отделе;
собственные объекты проверяются отдельно. Gateway также сверяет доступ к
конкретному анализу до выдачи результата, Review или Experience capture.

Права означают доступ к предусмотренным операциям API. Даже
`platform_admin` не получает произвольный SQL. Изменения роли имеют аудит;
отдельный журнал событий изменения членства и вкладка «Аудит» требуют
следующего шага.

## Сетевой контракт

Профиль Compose `identity` запускает миграцию и `user-service` во внутренней
сети без host-порта. `/internal/v1/*` требует
`Authorization: Bearer <USER_SERVICE_INTERNAL_KEY>`, который остаётся в
закрытом `.env`. Маршруты изменения роли и членства дополнительно получают
доверенный `X-PDRD-Actor-Id` от `admin-service` и сами проверяют полномочия
администратора. Поле `role` или Actor ID из браузерного запроса не считается
доказательством доступа.

Основные внутренние действия: разрешение и создание профиля, получение
текущих permissions, список пользователей, создание организаций и отделов,
чтение/изменение членства, замена рабочей роли и проверка области Review.
Публичный профиль `/api/v1/users/me` проходит через Gateway и Auth Service;
браузер не обращается напрямую к внутренним маршрутам.

Изолированная PostgreSQL-проверка использует `ops/compose.user-test.yaml` и
временную БД. После Windows quality gate её запускают на Linux:

```bash
docker compose -f ops/compose.user-test.yaml up \
  --build --abort-on-container-exit --exit-code-from user-test-runner
docker compose -f ops/compose.user-test.yaml down
```

Для первого администратора после подтверждённого корпоративного входа на
сервере выполняется `python -m pdrd_user_service.bootstrap_admin --user-id
<UUID>`. Команда одноразовая и не опубликована через HTTP.
