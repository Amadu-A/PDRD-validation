# Understanding без восстановительных VLM-запросов

Дата: 15.10.2026. Ветка `feature/quality`, исходный HEAD
`240e6e128c7ad7618ebf5318fd906245dd19f3ec` сверён с GitHub перед изменениями.

## Основание и границы

Контрольное задание пользователя: `78772b81-84d5-44de-83db-4a7396a6e3bc`,
внутренний документ `7e9f9ba0-fd7a-464b-a2a0-825d8ff03cf9`.
По приложенному журналу основной Understanding потребовал 17 обращений,
recovery — 29 (389,20 с провайдера и 804,63 с ожидания слота).
Это сумма затрат, а не гарантированное сокращение общего времени: одновременно
выполнялись другие задания. Отдельный основной запрос мог включать повторы адаптера.

Исправление затрагивает application-слой Analysis Service. Новых ports, DTO, таблиц,
миграций, секретов или настроек нет. Shared infrastructure, n8n, лимиты параллелизма,
кеш, N/T/U/D/E, Review и визуализация сохраняют свои существующие контракты.
Check Norms, Cross-page Consistency, Finalization и Graphical Refinement включены.

## Поведение

1. Надёжная чистая PDF-таблица сохраняет программный маршрут без основного запроса.
   Смешанный или визуальный лист делает один логический основной запрос. Его
   транспортные попытки учитываются отдельно и остаются ответственностью адаптера.
2. Схема основного ответа сохраняет все поля, типы, ограничения и ёмкость массивов.
   В D/EQ-записях неизвестные необязательные атрибуты можно опускать вместо множества
   пустых ключей. Все известные значения, условия, идентификаторы, исходные доказательства
   и области надо сохранять. Краткая сводка не заменяет атомарные факты.
3. `VisionModelOutputBudgetError` или `finish_reason=length` не запускает recovery.
   Даже синтаксически полный ответ с `length` не считается достоверным: его
   визуальные поля не переносятся в факты. Программные строки, количества,
   спецификация, происхождение и доступные детерминированные факты текста сохраняются.
4. Отсутствующие визуальные сведения остаются пустыми. Не создаются области,
   производители, нормативы или N/T/U/D IDs для заполнения результата. Check Norms
   получает неполные PAGE FACTS вместе с прежними исходными PAGE TEXT и изображением.
5. D и EQ независимы. При выключенном D доступные собственные инженерные факты
   текста после ограниченного извлечения передаются в Check Norms, но не объявляются
   найденными межстраничными D-источниками. Графические цели успешного основного ответа
   доступны и без D. Из переполненного ответа цели не угадываются.
6. Сетевые и инфраструктурные ошибки остаются ошибками. Отмена после основного
   запроса проверяется до продолжения, не выдаёт частичное задание за `completed`
   и сохраняет штатный механизм отмены HTTP-этапов.

Старые описания recovery относятся к историческим этапам. Актуальна эта политика.

## Диагностика и кеш

`understanding_page` и HTTP `metrics.understanding` содержат:

| Поле | Значение |
| --- | --- |
| `job` | Внутренний `document_id`, без текста документа |
| `main_request_count` | 0 для чистой таблицы, не более 1 для основного запроса на лист |
| `logical_request_count` | Все обращения к порту на листе, включая уточнения и кеш |
| `vlm_call_count` | Известные физические попытки адаптера; cache hit исключён, неизвестное число — `null` |
| `recovery_count` | 0; переполнение само по себе не recovery |
| `output_budget_count` | Логические обращения, завершившиеся переполнением: исключением или ответом с `length`; это не счётчик отдельных попыток адаптера |
| `cache_hits` | Число ответов из существующего кеша |
| `result`, `limited_reason` | `incomplete/output_budget`, `incomplete/empty_page_facts` или `incomplete/partial_page_facts`; обычный результат — `completed/null` |
| `programmatic_facts`, `text_facts`, `vlm_facts` | Программные факты таблиц/текста, отдельно текст и факты VLM |

Стоимость неудачного основного ответа не исчезает; неизвестные usage остаются `null`.
Cache hit имеет 0 физических попыток и токенов. Ключ кеша по-прежнему учитывает prompt
и schema: изменённый компактный запрос может дать холодный первый прогон. Ошибки
и усечённые ответы не кешируются как успешные. Полные страницы и промпты не логируются.

## Проверки и реальная приёмка

Автоматические тесты проверяют все D/EQ-комбинации, переполнение исключением и
валидным JSON с `length`, отсутствие recovery, один основной запрос, 65 исходных
строк с количествами, пустые/неполные PAGE FACTS, отмену, сетевой 503, настоящий
файловый кеш и независимое графическое чтение. HTTP-тест с настоящими маршрутом
и vLLM-адаптером проводит все 31 страницы от переполнения к Check Norms с исходными
текстом и изображением. Ответ провайдера в этих тестах имитируется.

До повторного реального прогона ускорение и сохранение инженерного качества
не считаются доказанными. Полный Windows gate: `ops/check-quality.ps1`.
Серверный gate: `bash ops/check-quality.sh`, журнал в `/tmp`.
Для этого исправления достаточно пересобрать и пересоздать `analysis-service`
после окончания активных анализов. Миграции и публикация workflow не нужны.

Порядок сравнения:

1. Сохранить старые result/status/visualization, полный журнал, SHA исходного PDF,
   настройки N/T/U/D/EQ, версии и условия конкуренции с другими заданиями.
2. Повторить все 31 страницы того же исходного PDF без экспертных пометок и без
   изменения источников. Записать новый публичный job_id и внутренний document_id.
3. Сохранить окно логов с timestamp. Выделить только нужный внутренний `document_id`:
   `understanding_page.job`, `vlm_slot_timing job=...`, `engineering_candidate.job`.
   Общие START/DONE без связи с документом и cache hits других заданий не приписывать ему.
4. Проверить `recovery_count=0`, отсутствие `:recovery:` в стадиях этого документа,
   `main_request_count<=1` каждого листа, все 31 результата Check Norms и завершение
   финализации. Чистые таблицы и cache hits не должны выглядеть как новые GPU-запросы.
5. Сравнить физические попытки по `provider_attempts` и метрикам, токены, ожидание
   слотов, время провайдера и фактическую длительность задания. Не суммировать
   повторно одни расходы из stage- и page-метрик. Отдельно отметить холодный/тёплый кеш.
6. По каждому H01–H35 из существующей экспертной матрицы записать: найдено/частично/
   пропущено/ложное совпадение, новый finding_id, страницы, evidence, области,
   применимые источники и причину ограничения/отклонения. Отдельно проверить
   H09, H16, H24, арифметические и табличные претензии. Не скрывать пропуски неполным
   Understanding и не подменять смысловую сверку общим числом замечаний.
7. Проверить UI через рабочий HTTPS, загрузку JS/CSS, запуск без сокращения страниц,
   отображение результатов, существующий Review и итоговый PDF. Отдельно отменить
   анализ при ожидании VLM и во время обработки: последующих запросов быть не должно.

Критерий принятия: меньше физических обращений и времени при корректном завершении;
все обнаруженные потери качества перечислены и оценены инженером.
