# Программная инженерная проверка проектных решений

Описание объединённого изменения `b4f1a04`. Последующая доработка расчётных
таблиц, режимов и допуска арифметических кандидатов описана в
[Quality, этап 1](quality-calculation-tables.md).

16 октября 2026. База `feature/quality`: `066f83f47e025b29b6ee276f4ebb8019910ca5d5`.
Пользователь объединил этапы A–D и контрольные проверки E в один будущий коммит.
Агент не выполняет staging, commit или push.

## Назначение и порядок

Прочитанные факты проходят последовательность:

`объект и принятое значение → исходные условия → расчёт/ссылка → применимое основание → проверка согласованности → вывод`.

`prepare_page_program` исполняется перед существующим смысловым Check Norms.
Он использует PageFacts, PAGE TEXT и уже полученные N/T/U-источники.
Результаты применяются к кандидатам после этого же вызова; второй вызов не нужен.
Межстраничная программа выполняется в существующем `/document-context/check-consistency`.
Исходные группы прежнего VLM-сопоставления сохраняются: новые программные наблюдения
не превращаются в дополнительные гипотезы для модели.

Understanding, recovery=0, Graphical Refinement, промпты, бюджеты вывода,
VLM concurrency, n8n и shared infrastructure не изменены. Код frontend также
не изменён. Проекция программных данных не расширяет действующие VLM-промпты.

## Реестр и протокол

`domain/design_decisions.py` сохраняет исходные DocumentFact/LocatedDocumentFact,
объект, систему, участок, режим, условия, смысл столбца, значения, страницы,
строки и области. Идентичность не устанавливается по похожему названию.
Неразрешённые объекты сохраняются отдельно, наблюдения не удаляются.
При выключенном D нет скрытого межстраничного объединения или источников D.
Обзор таблиц также разделяет режимы и, при выключенном D, физические страницы.
Общее назначение явно указанной системы можно связать с её режимами, не смешивая
принятые для разных режимов параметры.

Уже извлечённые VLM-факты допустимы для вычислений, когда исходная цитата буквально
подтверждена PAGE TEXT и содержит значение, точный объект, необходимые роли и условия.
Неоднозначные визуальные наблюдения сохраняются в реестре, но не становятся
детерминированным доказательством. Для вопроса о конкретном расчёте также нужны
подтверждённые принятое значение, исходные данные и ссылка.

`EngineeringCheck` содержит правило, статус, причину, исходные наблюдения,
вычисление, допуски, недостающие данные и ID переданных источников.
Протокол различает `confirmed`, `needs_review`, `no_finding`, `not_evaluable`.
Состояние последнего не означает, что решение безопасно или что обоснование
отсутствует во всём проекте.

Полный EngineeringReport существует внутри сценария и воспроизводится из
сохранённых фактов и исходного текста без VLM. Связанные проверки записываются
в существующие `origin_assertions` каждого finding. Полный локальный контрольный
снимок, включая решения без замечаний, экспортируется в `.codex-test-temp`.
Новый публичный endpoint полного реестра и новая БД не создавались. Поэтому
общий реестр без findings не добавлен самостоятельным полем финального API.

## Программные правила

| Механизм | Условия доказанности | Результат при недостатке данных |
| --- | --- | --- |
| Числовое равенство | Выражение и результат буквально записаны, только числовые +, −, ×, / | Не вычислять неизвестные переменные или скрытую формулу |
| Совместимые единицы | Известная размерность, Decimal, допуски округления | `not_evaluable` для неизвестных/несопоставимых величин |
| Внутренняя ссылка | Точное обозначение и фактически прочитанное определение | Конкретный вопрос о ссылке и проверенной области |
| Сумма таблицы | Полный набор строк, столбец, режим, конец таблицы и манифест покрытия строк | Ошибку суммы не подтверждать |
| Баланс напоров | Явные роли располагаемого/требуемого напора, один объект и режим | Не смешивать разные роли, давление и метры напора |
| Пожарный запас | Полезный объём, пожарный расход, длительность и явно установленная гарантированная подпитка | Общий геометрический объём и неизвестный приток не подставлять |
| Скорость в трубе | Один участок и режим, расход и внутренний диаметр либо наружный диаметр со стенкой | Конкретный вопрос об известных и недостающих данных; DN не подставлять |
| Суммарные потери напора | Тот же участок/режим, длина, внутренний диаметр, скорость, явный коэффициент Дарси и сумма местных сопротивлений | Не угадывать коэффициенты, не считать неизвестные местные сопротивления нулевыми |
| Проект/закупка | Полные сопоставимые перечни одного изделия/исполнения, единицы и известная упаковка | Не вычислять дефицит по неполному списку |
| N/T/U-порог | Точный объект, свойство, числовое ограничение, страница источника и условия | Похожий нормативный абзац не подтверждает применимость |
| Конфликт N и T/U | Два явно применимых несовместимых числовых ограничения | Конкретный вопрос об уточнении ТЗ; N не ослабляется |
| Обоснование | Назначение, исходные данные, разрешённый расчёт, успешные вычисления и применимый источник | Конкретный вопрос только при известном принятом значении, исходных данных и незамкнутой ссылке |

Для пожарного запаса используется только явный водный баланс
`V = max(0, Q − Qin) × t` в совместимых единицах. Отсутствие записи о подпитке
не означает нулевой приток. Правило не подменяет нормативное определение расходов,
количества одновременных пожаров или полезного объёма резервуаров.

Для круглой трубы скорость вычисляется по `v = 4Q/(πd²)`. Суммарные потери —
по `h = (λДарси × L/d + Σζ) × v²/(2g)`, с приведением единиц и допусками исходных
чисел. Внутренний диаметр можно вывести из явно прочитанных наружного диаметра
и толщины стенки. Коэффициент Фаннинга не используется как коэффициент Дарси;
неопределённые «потери» не считаются автоматически суммарными.
Математическая справка реализации — [DOE, Fundamentals Handbook, Fluid Flow,
уравнение 3-14](https://www.energy.gov/sites/default/files/2026-04/DOE-HDBK-1012-92_VOL3.pdf).
Это не нормативный N-источник для проектного замечания и не основание выбора
расхода, диаметра, скорости или обязательных пределов потерь.

Часовой и секундный расчётные расходы разных режимов не объявляются простым
пересчётом друг друга. DN и наружный диаметр не сравниваются как одна величина.
Разные карты ОСР и разные режимы сохраняют отдельные условия.
Продолженная таблица без доказанного конца не считается полной.

Арифметический интерпретатор не использует `eval`, не допускает функций, имён,
степеней и произвольного кода; размер выражения и AST ограничены.

## Соединения и функции

`domain/signal_connections.py` сохраняет явные рёбра
`шкаф/аппарат:клемма → шкаф/аппарат:клемма`, промежуточные контакты и реле.
Название клеммника другого шкафа не обязано совпадать. Путь не восстанавливается
по похожим обозначениям и не обходится через неизвестное промежуточное устройство.

Электрические параметры сравниваются на непосредственных концах ребра.
Для подтверждения нужны установленный потенциал, AC/DC и явно допустимый диапазон
входа. Для сухого контакта нужен питающий потенциал цепи: сам контакт не получает
фиктивного напряжения по названию модели. Противоречащие атрибуты не разрешаются
выбором последнего значения. Разные режимы и неустановленные связи остаются
ограничением проверки.

Назначение сигнала, NO/NC, безопасное состояние и режим управления проверяются
отдельно от электрической величины. Их различие может требовать смысловой проверки,
а не автоматически означать дефект. Отключение газа и электрического питания
сохраняются как разные действия. Не предлагается замена аппаратных защит ПЛК
ради уменьшения числа компонентов. Наличие пути не означает доказанной безопасности
всей функции аварийного останова, АВР или защиты двигателя.

## Оборудование, аксессуары и паспорта

Повторно используется существующий EQ pipeline, без нового чтения паспортов VLM.
Сравнение требует точной модели/исполнения и источника. Сохранены производитель,
модель, редакция, SHA, URL, физическая страница, параметр и цитата.
Несовместимая модификация исключается; непроверенный источник, неоднозначная
редакция или табличная применимость не подтверждают дефект.

Текстовое извлечение Knowledge Service и сравнение Analysis Service дополнены:

- тип RTD из явно перечисленных типов;
- число проводов датчика, с осторожной оценкой различий подключения;
- погрешность в совместимых единицах;
- явно перечисленные совместимые модели аксессуаров;
- монтажные размеры и явно допустимые диапазоны.

Модель прибора не используется как код напряжения питания. Характеристика
другой модификации не переносится. Экономия, наличие в магазине и пригодность
замены не устанавливаются без соответствующих данных.
Прибор не объявляется «гарантированно сгорающим» по неподтверждённой гипотезе.

EXTRACTOR_VERSION повышен с 7 до 8. Старые сохранённые EQ Facts обновляются штатным
механизмом версии извлекателя; очистка томов/документов или массовая переиндексация
нормативной базы не нужна. Новые характеристики не обрезают прежние записи
на лимите 100. Ограничения входных страниц существующего EQ API не расширялись.

## Финализация, дедупликация и локализация

Программный вывод перед Finalization повторно вычисляется по сохранённым фактам.
Сверяются правило, результат, формулировка и рекомендация. Категория finding,
флаг `confirmed` или наличие EQ-источника сами по себе не заменяют доказательство.
Подменённый расчёт или текст не проходят как защищённое замечание.
Подтверждённые программные findings не вызывают дополнительную VLM-финализацию,
включая случай найденных N-кандидатов для enrichment.

Табличный кандидат модели без установленной программной суммы становится
отдельной гипотезой с сохранением исходного текста, источников и причины.
Он не превращается автоматически в ручное Review-замечание.

Программные повторы объединяются только при одинаковом объекте, свойстве,
условиях, правиле и полном смысле вычисления/основания. Разные ограничения
источников, исходные числа, области таблиц и независимые свойства не затираются.
При объединении сохраняются страницы, области, все N/T/U/D/EQ и история.

Новые рамки получают координаты только из существующих областей фактов или
PDF-слов. Если координаты не установлены, новое программное замечание остаётся
без точной рамки: отдельный VLM fallback для него запрещён. Старые findings
сохраняют прежний путь локализации. Frontend/Review и их геометрия не изменены.

## Проверки и реальные ограничения приёмки

Автоматические проверки охватывают факты → правила → finding → HTTP → Finalization
и локализацию, несовместимые единицы/режимы, неполные таблицы и перечни, упаковки,
неподходящие исполнения, сухой контакт, отдельные защитные действия, N/T/U-конфликты,
повторы/независимые претензии, подмену доказательства, D=false/E=false/EQ=false
и архитектурный запрет новых обращений модели.
Большой синтетический реестр проверяется без GPU с ограничением времени.
Полный quality gate включает существующие проверки Review и PDF-экспорта.

Точные результаты gate и локальных PDF-прогонов сохраняются в отчёте агента и
`.codex-test-temp/engineering-complete`. Реальные модельные токены, физические
запросы, cache hits, ожидание GPU, время провайдера и полная длительность задания
не заменяются mock-значениями. Недоступное измерение обозначается `not_measured`.

Итоговый Windows gate: 2622 Python-теста прошли, 115 штатно пропущены,
376 JavaScript-тестов прошли, Ruff/format/diff чистые. Pytest занял 95,83 с.
Новые проверки программы и реестра отдельно: 90 тестов за 0,52 с, без GPU.
Лог: `.codex-test-temp/engineering-handoff-quality.log`.

Контрольное воспроизведение Check Norms относительно `066f83f` на одном входе:
запрос целиком совпадает (prompt/schema/seed/image/budget); один существующий
вызов до и после. Модель в mock вернула пустой список, программа нашла ошибку
числового равенства, финализация добавила ноль вызовов. Этот результат доказывает
путь интеграции, но не качество ответа настоящей модели.

Программный проход всех доступных PDF без Understanding/retrieval дал:

| Документ | Страниц | Наблюдений в реестре | Решений | Findings |
| --- | --- | --- | --- | --- |
| Контрольный ИОС2.2 | 31 | 63 | 38 | 0 |
| Независимый ИОС 4.1.7 | 31 | 530 | 528 | 1 вопрос инженеру |

Наблюдения включают исходные факты и дословные зависимости из текста. Время

Это не полное время анализа и не оценка скорости тёплого GPU-кеша.
По основной экспертной матрице новых подтверждённых совпадений этим проходом
не получено. Цель повышения инженерного качества пока не подтверждена.

H01–H35 остаётся исключительно offline-матрицей. Новый положительный результат
на настоящем VLM-прогоне пока не подтверждён. Успех unit-теста не является
доказательством роста инженерного recall. Отдельные 12 сценариев АТМ/ЭОМ также
не выдаются за инженерную разметку реального проекта.

В предоставленном каталоге доступны контрольный ИОС2.2, ИОС 4.1.7 и охранная
сигнализация. Полного комплекта ЛСУ/котла/ВРУ, закупочной ведомости и паспортов
нет. Действующие HTTP-контракты не передают полный многодокументный проект;
U retrieval не доказывает комплектность. Эти материалы не объединяются
между пользователями/заданиями. Новый проектный API без отдельного решения
не вводится. Поэтому межшкафная приёмка на таком комплекте остаётся невыполненной.

## Установка одного объединённого коммита

Пользователь выполняет Windows gate, просмотр полных файлов, явный staging,
commit и push. Список файлов и полные тексты находятся в локальном комплекте
`.codex-test-temp/engineering-complete`, не в новом operational script.

На сервере после push, без активных анализов:

```bash
set -euo pipefail
cd ~/projects/PDRD-validation
git remote get-url origin  # приватный neo-term-it/PDRD-validation
git pull --ff-only origin feature/quality
bash ops/check-quality.sh > /tmp/pdrd-engineering-quality.log 2>&1
bash scripts/up.sh > /tmp/pdrd-engineering-up.log 2>&1
bash scripts/check-stack.sh
```

Используется штатный `up.sh` со встроенной сборкой и проверкой readiness.
Изменённый прикладной код расположен в analysis-service и knowledge-service;
конфигурация стека не менялась. n8n импортировать не нужно. Новых миграций нет.
После установки проверить старый Review:
добавление, обе рамки, текст, решения, сохранение/перезагрузка и два PDF.
Затем выполнить полный ИОС2.2 1–31, независимую сигнализацию и D/EQ-переключатели,
проверить отмену. Сверить H09/H16/H24 и остальные H01–H35 по смыслу с инженером.
Снять фактический VLM baseline и новый прогон на одинаковых настройках/кеше,
разделяя document_id и job_id и не суммируя параллельные длительности.
