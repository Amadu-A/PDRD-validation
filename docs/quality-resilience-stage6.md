## Что установлено о 503

Действующий embedding API `/version` сообщает vLLM `0.29.0`. В этой версии приведённая в ТЗ фраза соответствует `QueueOverflowError`: превышен лимит незавершённых запросов, учитывающий ожидающие и выполняющиеся последовательности. Это проверено по [исключениям vLLM 0.29.0](https://github.com/vllm-project/vllm/blob/v0.29.0/vllm/exceptions.py) и [проверке admission](https://github.com/vllm-project/vllm/blob/v0.29.0/vllm/v1/engine/async_llm.py). Переполнение prefill-токенов имеет другое сообщение. Доказательств OOM нет.

Установлен механизм отказа. Какой поток и какой фактический лимит привели к переполнению на конкретном `itemIndex=7`, пока не установлено. `/server_info` возвращает 404; `/metrics` доступен, но на момент проверки `running=0`, `waiting=0`. Настройки из shared Compose являются defaults, не доказательством параметров запущенного процесса. Журналы отказа и идентификатор/файл задания B запрошены отдельно; повторных SSH-попыток не было.

До изменения text-адаптер терял временную классификацию, общего допуска API/индексаторов не было, управляющий retry отсутствовал. Узел n8n мог повторно отправлять весь поисковый HTTP-запрос. Дополнительные N-first темы увеличивали число последовательностей внутри embedding batch. Число HTTP-запросов нельзя приравнивать к числу последовательностей в очереди модели.

## Реализованные изменения

- Общий runtime text/image: ограниченная FIFO, физический допуск через существующий PostgreSQL session advisory lock для API и индексаторов N/T/E/мигратора. Новых таблиц нет. Локальная очередь ограничена; глобальные слоты ограничивают запросы PDRD, а не всех клиентов shared модели.
- Text batch до 4, image по 1; ограниченные временные повторы, exponential backoff/jitter, `Retry-After`. До четырёх повторов по операции; пятый отказ или исчерпание 120 секунд завершают её. Успешные микропорции не повторяются. Во время backoff слот освобождён.
- Gateway предоставляет внутреннее чтение lifecycle без изменения progress. Отмена проверяется в ожидании и перед новым inference; deadline не продлевается. Ожидаемая отмена имеет отдельный ответ; постоянный отказ не становится пустым набором норм или `completed`.
- В трёх repository workflow отключён дополнительный retry embedding-узлов. Batching [HTTP Request n8n 2.34.5](https://github.com/n8n-io/n8n/blob/n8n%402.34.5/packages/nodes-base/nodes/HttpRequest/V3/HttpRequestV3.node.ts) задаёт только частоту запуска items; фактическое число запросов ограничивает backend. До строгих обработчиков источников добавлен IF: отмена любого item завершает весь batch одним штатным ответом, без разреживания страниц. Сборщик метрик использует явные имена узлов: архитектурный запрет динамического селектора и передачи всей истории Runner сохранён.
- Кэш точных нормализованных input ограничен заданием, моделью/размерностью, инструкцией и изображением. Вектор возвращается на каждую исходную позицию; результаты поиска и source/page IDs не кэшируются вместо повторного применения scope. Семантически близкие самостоятельные требования не объединяются.
- Общий запрос титульного листа/содержания освобождён от служебного текста при отсутствии инженерного плана; самостоятельные темы, факты, полный T-first feed и ID сохраняются.
- N-first больше не выключает прежний `check_requirement()`. Сохраняются прежние поддержанные N/T/U-классы, включая мощность; неизвестная редакция и квалификаторы предмета не обходят доказательный gate. Старые и новые совпадающие проверки объединяются по ограничению и объекту; конфликтующее T/U не превращается в подтверждённое нарушение.
- Насосы жидкого топлива отделены от водоснабжения по физическому предмету, а не по номеру СП. Смежный источник не удаляется из протокола; релевантное междисциплинарное положение допускается.
- Из явных проектных решений программно формируются вопросы о составе пожарного запаса и защите конкретных объектов. Новых VLM-вызовов для шагов не добавлено. Учитываются существующие типы исходных данных и ссылок; вопрос о полноте снимается при их наличии. Геометрические объёмы не выдаются за полезный запас.
- Исправлена потеря чисел/ссылок перед конечной точкой; часть десятичного значения по-прежнему не считается отдельным числом. Верификация программного вопроса сверяет принятое решение и недостающие данные с фактами, а не с подменёнными метаданными.

`frontend/src`, обработчики Review, его права, геометрия, сохранение и PDF-рендеринг не менялись. Прогон содержит регрессии интерфейса; ручная приёмка сервера остаётся необходимой.

## Диагностика

`GET /api/v1/analyses/{job_id}/diagnostics/normative` возвращает компактную проекцию сохранённого завершённого результата, с теми же проверками владельца/гостевого доступа. Здесь страницы, базовые/дополнительные/уникальные запросы, физические запросы embedding, batch sizes, 429/503/timeout, причины отказов, retry/ожидание, N/T/U, исходы/причины/редакции/применимость плана и судьба программных N-кандидатов. Повторная копия метрики не удваивает операцию; разные проектные значения одной нормы не затирают друг друга.

`unique_inputs` — сумма уникальных input отдельных embedding-вызовов, а не число уникальных тем всего документа. Для N-тем есть отдельный `unique_document_queries`. `provider_ms` включает HTTP и серверное ожидание; это не чистое время GPU. `wait_ms` показывает admission/backoff клиента. Историческая отсутствующая телеметрия возвращается как неизвестная, не как ноль.

При аварии обязательного поиска результат не публикуется как успешный. Короткие события `embedding_retrieval` сохраняют job/document/operation/stage и счётчики без текстов и векторов. Полные протоколы плана остаются в существующих метриках результата. Метрики индексирования имеют свой stage и document ID.

Рабочее значение не менялось; по ТЗ у сервера сейчас `true`. Решение о включении следует пересмотреть по реальному парному прогону и квалификации инженером.

## Публикация и ручная проверка

Использовать существующие скрипты: Windows quality gate, затем пользовательский commit/push; на сервере private pull → `bash ops/check-quality.sh` → `bash scripts/up.sh` → `bash scripts/check-stack.sh`. `origin` локальной копии уже имеет два push URL (публичный и приватный репозитории), поэтому обычный push отправляет в оба.

После пересборки — **Import → Save → Publish всех трёх** `n8n/workflows/analysis-v2-*.json`. Пересборка не публикует shared n8n. Сопоставимые A/B запускать последовательно: одинаковые исходники/SHA, snapshot N/T/U, флаги D/PZ/E/EQ, модельные параметры и версии workflow; менять только N-first. Сохранить краткую `/diagnostics/normative`, результат и версии. Для B проверить завершение поиска и диагностируемый отказ; перегрузку GPU вручную не создавать.

В интерфейсе: блокировка анализа без раздела, доступность после раздела/файла; корректные Understanding/T-first/Check Norms/Finalization; отмена во время ожидания; создание, изменение текста/обеих областей, удаление, принятие и сохранение Review после перезагрузки. Автоматический `/annotated-pdf` и итоговый `/reviewed-pdf` проверить отдельно. Новый вопрос не должен становиться нарушением нормы без доказательств; H02 не должен выдавать 250 м³ за полезный запас.

Локальные диагностические артефакты — `.codex-test-temp/quality-resilience/`: `embedding-runtime-probe.json`, `embedding-runtime-limits.json`, `baseline-replay.json`, `current-replay.json`, `replay-comparison.json`, `ab-programme.json`, `matrix-comparison.json`, `quality-final.log`, `source-manifest.json`, `full-source.txt`. Они игнорируются Git; не заменяют серверную приёмку.
