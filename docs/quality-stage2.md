# Quality, этап 2: сопоставимость и сохранность инженерных выводов

Подготовлено поверх `a44d300` в `feature/quality`. Код не закоммичен, не отправлен и не развёрнут агентом.
Полная инженерная приёмка остаётся открытой: H10 не восстановлен на исходном снимке фактов,
повторный анализ после Linux-деплоя ещё не выполнен.

## Что установлено

Последнее вложение — обрезанный фрагмент PDF-derived JSON размером 6949 байт.
Оно начинается внутри списка аннотаций предыдущей записи, содержит запись №14 о резервуарах
и обрывается внутри записи №15. Это не оригинальный API JSON задания
`ba084c28-cc31-420e-85ab-22f0081b789d`. Блок про сухотруб присутствует только частично.
По этому вложению нельзя восстановить все замечания, backend finding_id или пользовательскую геометрию.
GET status/result указанного задания через доступный адрес API вернули 404.
Новых путей, файлов или логов у пользователя не запрашивали.

### H09

Потеря воспроизведена на действующей `shared-vlm`, а не только на моках.
Использовались одинаковый исходный PDF, сохранённые извлечённые факты, нативные PDF-слова,
настройки проверки и модель. В `a44d300`:

1. Подписи назначения системы есть в PageFacts на физических страницах 8, 13, 14.
2. Document Context сохраняет их; Conflict Discovery создаёт `C4`.
3. Cross-page Validation в трёх прогонах отклоняет `C4` с `reason_code=different_object`.
   Ответ предполагает разные системы В2 в разных контекстах; такой контекст не доказан исходными записями.
4. Пользовательский finding не создаётся. Candidate Merge и Finalization уже не получают H09.

Таким образом, в этом воспроизведении потеря находится **до Finalization**.
Дополнительный дефект: discovery использовал исходный `subject_type`, хотя единое инженерное
утверждение уже канонизировало назначение сети. `network` и `system` могли разбить одну группу.

Теперь явно подписанные взаимоисключающие назначения водоснабжения/водоотведения одного
идентифицированного объекта при одинаковых условиях проверяются программно.
Проверяются физические страницы, цитаты, объект, значения и условия через действующий evidence-аудит.
Непроверенный визуальный факт, иной объект, иное условие или совместимые назначения не проходят этот маршрут.
Назначение не выводится из самого тега, код В2 не зашит в правило. Finalization повторяет доказательство.

При пустом ответе модели H09 также сохраняется. У `a44d300` он остаётся `unassessed`;
исправленная версия создаёт доказанный finding без отдельной генерации.

Это локализация потери в контролируемом воспроизведении. Без исходных стадий последнего job
нельзя утверждать, что его внутренняя последовательность была полностью идентична.

### Влияние a44d300

`text-pool-v1` восстанавливает исходные строки до Pydantic и application-логики.
Новый функциональный тест передаёт 31 страницу с N/T/U/D/ПЗ, одинаковыми цитатами на разных страницах,
разными ID/point_id, условиями и областями. Восстановленные DTO и программные отчёты равны исходным.
Предыдущие тесты опубликованного JavaScript-упаковщика также сохранены.
Native-текст не заменяется ПЗ; источник с другой физической страницы остаётся отдельным источником.

Изменения компактного Check Norms prompt не являются установленной причиной H09:
в воспроизведении кандидат отклоняется раньше этого маршрута.
На его решение влияет состав и порядок межстраничного batch: старая версия передавала H09 первой,
`a44d300` — четвёртой. Это показывает зависимость свободного решения модели от контекста,
но не доказывает единственную причину всех исторических регрессий.

### H10

В нативном тексте страницы 13 извлекается общая протяжённость сети 147 м.
Просмотр исходного PDF подтвердил: на странице 26, позиция 6, в группе противопожарного
водопровода указано **150 м трубы** в колонке количества. Нативного текста этой строки нет:
спецификация изображением. В доступном сохранённом снимке PageFacts нет сопоставимого факта 150 м.
Следовательно, на этих данных H10 не доходит даже до Conflict Discovery.

Исправлены общие идентификаторы `network/system` и алиасы свойств длины, включая структурированный
`network_total_length`. Регрессия с двумя полными исходными утверждениями о длине сети проходит.
Но тест с вручную заданными фактами не считается обнаружением строки сканированной спецификации.
Система не получает фиктивный факт 150 м из экспертной матрицы.

Количество поставляемой трубы не равно автоматически протяжённости сети: нужны запас, границы
учёта, состав материала и условия. Для данного PDF сначала требуется сохранение строки спецификации
в структурированных данных, затем предметный вопрос о сопоставимости. Объявлять разность 147/150
доказанным нарушением без этой проверки нельзя. Это конкретная оставшаяся причина непрохождения H10.

## Предметные исправления

- Признаки разных элементов проверяются до превращения неполной цитаты в вопрос инженеру.
  Сухотруб и основной трубопровод, футляр и труба не сравниваются как один элемент.
- DN и наружный диаметр остаются разными определениями. При этом сопоставимые размеры одного
  доказанного участка продолжают проверяться действующим механизмом.
- Родовое имя резервуара не устанавливает идентичность отдельной ёмкости.
  Номинальные объёмы разных резервуаров не становятся противоречием. Сравнение подписанного Р1
  с тем же Р1 не отключено. Состав 2 × 100 + 1 × 50 читается из количества/перечня и сохраняется
  в протоколе вопроса обоснования; он не объявляется полезным противопожарным запасом.
- Суточный расход имеет собственную размерность. Объём, секундный и часовой расходы с ним не смешиваются.
- Роли величин канонизируются по смысловым корням: средний/максимальный, гарантированный/требуемый,
  водопотребление/водоотведение. Явно разные роли не сопоставляются. Незаписанная роль остаётся
  ограничением доказанности, а не автоматически противоположной ролью.

### Таблица 1 на страницах 14–15 и H16

На исходных PDF-словах воспроизведены три дефекта:

1. Слишком большой отступ от шапки пропускал первую строку.
2. Боковые надписи рамки попадали в название потребителя.
3. Строки следующего листа без повторённой шапки не относились к продолжающейся таблице.

Парсер сохраняет первую строку, отделяет боковую рамку и связывает верхний фрагмент соседнего листа
по открытой нижней таблице и согласованным колонкам. Новый заголовок/вводный текст ограничивает связь.
Полнота всех строк из наличия продолжения не выводится. Новая таблица 2 остаётся самостоятельной.
Заголовок единицы и его область принадлежат странице 14, ячейка и область значения — странице 15.
Каждый source_fragment повторно сверяется со своим физическим листом.

Условия в колонке «Примечание» также учитываются, если они явно описывают режим.
Благодаря этому сопоставляются строки подпитки с 0,5205 и 0,205 л/с.
При неполной определённости области учёта результат остаётся вопросом инженеру с обеими страницами,
а не утверждением о правильности одного числа. H24 и прежние предметные вопросы сохранены.

## Судьба кандидатов и объём данных

Discovery возвращает причины исключения геометрических фактов.
Межстраничные записи сохраняют исходный ID, все факты, evidence-аудит и результирующий finding_id.
Объединение отражается как `merged`, а не пропажа кандидата. Диагностическая гипотеза не считается
сохранённым пользовательским замечанием. Пропуск ответа не становится `refuted`.

В Finalization добавлен `metrics.candidate_fates`: сохранение, объединение, отклонение или отсутствие решения.
Тяжёлые доказательства не копируются повторно: для сохранённого finding есть ссылка на итог,
для уже сохранённой диагностики — ссылка на `rejected_findings`. Если исходный отвергнутый/непроверенный
кандидат нигде больше не сохранён, он записывается полностью. Исходная формулировка сохранённого кандидата
остаётся в компактном снимке. Все N/T/U/D/EQ-источники и геометрия остаются в результате/истории.
Отдельные findings автоматически визуально не группируются.

## Нормативный маршрут

Диагностика сообщает получение корпуса, активные поколения, отбор, состояние подготовки,
поддержку интерпретации, reason_code каждого ограничения, статусы N-кандидатов и вход/выход Finalization.
Отсутствие `normative_corpus` и ненастроенный независимый обработчик различаются явно.
`corpus_state=ready` означает чтение поколений, а `proof_state` отдельно показывает проверенность оснований.

В локальном фиксированном snapshot:

- 5796 атомарных требований; 5585 отобрано, 211 исключено по классу объекта.
- 5572 отобранных требований не поддержаны интерпретатором; 13 проходят этот уровень разбора.
- Причины: 5396 `atomic_interpretation_requires_review`, 176 `unsupported_requirement_rule`,
  4 `project_object_or_property_not_observed`, 8 `normative_edition_or_binding_unverified`,
  1 `requirement_conditions_not_established`.
- Проверенных сведений о редакции/обязательности в локальном snapshot нет; все 5585 имеют `currency=unknown`.
- Подтверждённых N-кандидатов и вопросов N — 0. Это ограничение подготовки/интерпретации корпуса,
  а не доказательство нормативной корректности проекта.

Это **локальные** показатели snapshot, не измерение состояния нормативной БД последнего серверного job.
Редакция, применимость и evidence-фильтры не ослаблялись. Переиндексация не выполнялась.
Сам N-first, embedding, модель и параметры VLM не переписывались.

## Поставка одним коммитом

Полные изменённые исходники: `.codex-test-temp/quality-stage2/quality-stage2-sources.zip` и `full-source.md`.
Точный список: `.codex-test-temp/quality-stage2/staging-paths.txt`.

Windows PowerShell из корня репозитория:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\ops\check-quality.ps1 -Fix > .codex-test-temp\quality-stage2\quality-user.log 2>&1
if ($LASTEXITCODE -ne 0) { Get-Content .codex-test-temp\quality-stage2\quality-user.log -Tail 120; throw "Quality gate не пройден" }
git diff --check
git diff --stat
git add --pathspec-from-file=.codex-test-temp/quality-stage2/staging-paths.txt
git diff --cached --check
if ($LASTEXITCODE -ne 0) { throw "Проверьте staged diff" }
git diff --cached --stat
git commit -m "fix(quality): preserve comparable cross-page engineering findings"
if ($LASTEXITCODE -eq 0) { git push origin feature/quality }
```

`origin` имеет два действующих push URL: публичный Amadu-A и приватный neo-term-it.
Проверка при необходимости: `git remote get-url --push --all origin`.
Уже staged пользовательские файлы этот manifest не убирает; перед коммитом нужно проверить общий staged diff.

Linux после пользовательского push:

```bash
cd ~/projects/PDRD-validation
git pull --ff-only origin feature/quality &&
bash ops/check-quality.sh > /tmp/pdrd-quality-stage2-quality.log 2>&1 &&
bash scripts/up.sh > /tmp/pdrd-quality-stage2-up.log 2>&1 &&

```

Quality script включает существующие изолированные интеграционные проверки сервисов.
`scripts/up.sh` выполняет штатную сборку, запуск и необходимые существующие миграции/readiness.
Новых миграций нет. При сбое смотреть хвост соответствующего `/tmp/pdrd-quality-stage2-*.log`.
Workflow не изменены: **Import → Save → Publish не нужен**.

## Ручная приёмка после деплоя

1. Авторизоваться; выбрать раздел; запустить исходный PDF без ТЗ, включив D, ПЗ и поиск оборудования.
   Все 31 страницы должны пройти до Finalization без 500; T-источников при отсутствии ТЗ быть не должно.
2. Проверить H09 с физическими страницами 8/13/14 и H16 с 15/30; сохранить H24 и предметные вопросы H02/H08/H12/H18.
   H10 пока не считать восстановленным по исходному скану. Одиночный успешный прогон не доказывает стабильность.
3. Не должно появиться противоречий только из DN100/Ø110, сухотруба/основной сети или резервуаров 100/50.
   Отсутствие строки таблицы 1 нельзя обосновывать одним её первым листом.
4. Проверить diagnostics независимого N-прохода: наличие scope, реальные generation_id, coverage/reason_codes,
   `proof_state` и `normative_route` Finalization. Ноль N-замечаний сам по себе не означает успешную нормативную проверку.
5. В Review добавить, отредактировать, удалить и утвердить замечание; изменить обе области;
   сохранить и перезагрузить страницу. Сохранённые пользовательские координаты должны совпасть.
6. Скачать автоматический `/annotated-pdf` и итоговый `/reviewed-pdf`; независимые карточки/области и источники
   должны сохраниться. Проверить прогресс, отмену, авторизацию и EQ-отчёт.

Следующий этап до результатов этой проверки не начинается.
