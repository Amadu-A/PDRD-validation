# Атомарная индексация: результаты проверки 22.10.2026

## Что установлено по серверной диагностике

Присланный вывод содержит 17 разделов и 285 нормативных документов:
284 chunk-ready, один failed. Атомарных поколений и требований нет,
журнал нормативного статуса пуст. Qdrant alias `dva_catalog_active` содержит
28147 точек, из них 846 для ИОС2. Эти числа относятся к присланному состоянию,
а не к выполненному этой сессией production backfill.

Подтверждённый дефект кода — раздельные транзакции READY и постановки atomic job,
ранний выход при повторе READY и отсутствие backfill/reconciliation старой библиотеки.
Исправление и команды поставки описаны в [инструкции](atomic-normative-recovery.md).

## Проверка настоящих локальных СП

Четыре имеющихся PDF СП проиндексированы настоящим extractor/worker в собственном
изолированном PostgreSQL 16.15 с текущими миграциями. После публикации реальные
строки прочитаны через Knowledge HTTP API и `HttpNormativeRequirementsReader`.
Затем выполнен `IndependentNormativeReview` по сохранённым 245 фактам исходного
31-страничного PDF ИОС2.2; native text взят из самого PDF.

Это локальный replay фактов, а не новый Understanding и не полный серверный E2E.
SHA проекта: `76e3f20c20bd0ab570d04ee93916928c9a56d432045afb3ed5fc46470f49cdfa`.
SHA нормативных оригиналов, generation IDs, manifest/digest и результаты сверки
реальных строк находятся в локальном `native-audit.json` комплекта проверки.

В процессе проверки исправлен счётчик: записи с
`unsupported_requirement_rule` больше не считаются поддержанными только потому,

Это подтверждает восстановление хранения и чтения атомов, но одновременно
показывает низкую функциональную полноту текущей нормативной грамматики.

поддержка структурированных условий/таблиц/зависимостей и проверяемые правовые
свидетельства. Добавление произвольного mandatory ради положительного результата
не выполнялось.

## Сквозной положительный и отрицательный контроль

Отдельный тест создаёт учебный нормативный оригинал с требованием расхода
не менее 5 л/с, сохраняет извлечённые worker атомы и учебное свидетельство,
затем использует настоящий HTTP reader, N-first и Finalization.
Никакие готовые findings в extractor/reader не подставляются.

- 4 л/с: одно подтверждённое замечание, сохранены документ, 5.1, страница,
  буквальная цитата, SHA и происхождение.
- 5 и 7 л/с: ложных замечаний нет.
- VLM не вызывается; неожиданный вызов проваливает тест.

Тест проверяет механизм. Учебное свидетельство не подтверждает статус настоящего
СП и не переносится в рабочую базу. На настоящих локальных нормах отсутствие
подтверждений остаётся функциональным блокером для confirmed N-нарушения.

## Регрессии и инфраструктура

Проверены dry-run/status без побочных эффектов, все 285 документов и пустой
раздел, ограниченный backfill 284 READY, повтор без дубликатов, очередь/outbox/worker,
восстановление stale/failed, backoff/лимит попыток, смена snapshot при занятых
слотах, rollback READY/outbox, предыдущий active, повреждённые строки/digest,
полнота страниц, выборочный CPU OCR, DOC/DOCX preview provenance и очистка sidecar.
Сквозные frontend проверки сохраняют существующие Review/resize/export сценарии;
добавлен тест независимости основного каталога от зависшего atomic-readiness.

Целевой набор с полным 285-документным сценарием: 69 тестов за 39.68 с,
включая проверки атомарного каталога и независимого N-first. Имитация БД использует
copy-on-write неопубликованных порций; SQL-транзакции отдельно проверены настоящим PG.
Изолированный Knowledge integration на PostgreSQL: 29 passed, 6 skipped
(дополнительные Qdrant/owner/retention профили не подключались).

Финальный общий Windows gate: Ruff успешно, pytest — 3164 passed, 120 skipped,
192.22 с; весь frontend — 403 passed; `git diff --check` успешно.
Полный вывод записан в release-лог комплекта проверки. Skipped — отдельные
runtime/инфраструктурные профили, не заменённые фиктивными успешными проверками.

Linux Docker gate и production readiness этой сессией не выполнены:
локальный Docker daemon недоступен, сервер отклонил настроенный SSH-ключ.
Коммит, push, развёртывание, production backfill и повторный полный серверный анализ
не выполнялись. В инструкции приведён штатный порядок dry-run → пилот → backfill
→ проверка Qdrant → полный PDF с положительным/отрицательным контролем.

Нельзя считать локальный unit/replay полноценным серверным E2E или измерением
совпадений H01–H35. Результат на всей библиотеке — отдельная обязательная приёмка
после поставки. Workflow n8n не менялись; повторный Import → Save → Publish не нужен.
