# EQ: идентификация, долговечная проверка и обновление Review

## Идентификация

Производитель подтверждается отдельным дословным доказательством из текстового
слоя проекта. Предположение VLM не назначает производителя. Если маркировка
модели подтверждена, допускается предварительный поиск с неизвестным
производителем; инженерная находка появляется после проверки документа.
Порты, интерфейсы, линии и условные обозначения исключаются из реестра изделий.

Для контрольного двухстраничного PDF распознаются шесть уникальных моделей.
`2RS485` является интерфейсом, «Эстет-Сейф», «Арфа», «Пирон-Ш» — наименованиями,
`исп. 51` — исполнением. В реестре сохраняются вхождения на обоих физических
листах, области, параметры и артикулы. Артикулы разных изделий не сливаются.
Незначащие пробелы, типографские дефисы и запись «исполнение» нормализуются.
Число в маркировке `РИП-12` не является доказательством проектного напряжения.
Неподтверждённые параметры сохраняются с `evidence_status=needs_review` и
не создают автоматического расхождения.

Регрессионный файл: `tests/fixtures/equipment/security-alarm-two-pages.pdf`.
SHA-256: `9765d853519f7f4a7c5f338c9e38fade5537cd6c42e03a46179055034e9afe11`.
Тест использует реальные страницы и текст PDF и управляемый ответ VLM,
воспроизводящий исходные ошибки. Он проверяет защиту обработки, качество
реальной модели отдельно измеряется на сервере.

## Очередь и квоты

| Настройка | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `MAX_MODELS` | 500 | Уникальные модели в логической проверке |
| `QUERIES_PER_MODEL` | 3 | Первый запрос, затем до двух дополнительных |
| `DOWNLOADS_PER_MODEL` | 2 | Одна загрузка за попытку, ограниченный повтор |
| `INLINE_MODELS` | 20 | Более крупное задание возвращается в фоне |
| `BATCH_SIZE` | 10 | Порция перед возвратом в долговечную очередь |
| `MAX_SECONDS` | 180 | Таймаут одной попытки |
| `MAX_CONCURRENT_SEARCHES` | 2 | Сетевые попытки; слот освобождается между моделями |
| `MAX_VISION_CALLS` | 2 | Начальная общая квота VLM; ноль отключает VLM |
| `ADAPTIVE_VISION_CEILING` | 8 | Верхняя граница адаптивной квоты VLM |
| `MAX_RESUME_RUNS` | 3 | Явные продолжения по ожидаемой версии |

Префикс настроек: `EQUIPMENT_SEARCH_SERVICE_`. Значения остаются в
`.env.example`, приватный `.env` хранит секреты и нужные переопределения.
Старые `MAX_QUERIES=6`, `MAX_DOWNLOADS=3` задают минимальные квоты малого задания.
Верхние ограничения одного запуска: 1500 запросов, 1000 попыток загрузки.
VLM квота вычисляется как минимум потолка и максимума начальной квоты и
`ceil(число моделей / 50)`. Она общая для задания, не выдаётся каждому изделию.
Повторное чтение VLM кэша не расходует GPU квоту.

Каждая допустимая модель проходит первоначальное разрешение раньше повторов.
Готовый локальный документ переиспользуется без поискового запроса. Для
очереди чередуются приоритет коротких проверок и давно ожидающей порции.
Число локальных задач ограничено; очередь хранится в PostgreSQL.

Миграция Equipment `20261012_0004` добавляет checkpoint, политику, ревизию,
число продолжений, `job_models`, `job_versions` и отдельный артикул документа.
Checkpoint обновляет одну строку модели и небольшое состояние задания.
Полный JSON результат записывается при завершении версии. Отмена и
проверка флага остановки не читают весь массив оборудования на каждой ссылке.

До внешней операции сохраняется резерв квот. При аварии фактический результат
операции может быть неизвестен; резерв остаётся израсходованным, чтобы
перезапуски не обходили ограничения. Запись `operation_interrupted` объясняет
это в диагностике. Подтверждённые результаты сохраняются после рестарта и
продолжения. При явном продолжении новые квоты выдаются только нерешённым
позициям, число таких запусков ограничено сохранённой политикой. По умолчанию
суммарный предел VLM на первоначальный запуск и три продолжения — 32 вызова;
обычный рестарт дополнительный бюджет не выдаёт.

Работает один процесс Equipment Service. Общий GPU limiter остаётся в одном
процессе Analysis Service. Реплики этих сервисов требуют отдельного решения
для распределённого ограничения и владения заданиями.

## Документ и диагностика

Кандидаты одной поисковой выдачи устойчиво ранжируются: официальные записи
начального реестра, остальные включённые trusted источники (в том числе
подтверждённые каталоги), затем pending/неизвестные при разрешении пользователя.
Признак официальной записи читается из существующего `registration_source`,
который миграции реестра заполняют проверенным HTTP(S)-адресом производителя.
Ручные записи сохраняют `manual`, автоматические — `web_search`. Это приоритет,
а не новый статус доверия: disabled/blocked и проверка применимости сохраняются.
Первый запрос по доверенному домену также выбирает официальный источник раньше
остальных подтверждённых доменов.
Для вручную зарегистрированного официального сайта отдельная классификация
не вводилась; он относится к группе других подтверждённых источников.

`link_model_mismatch` означает отрицательную проверку заголовка/пути ссылки до
загрузки. Отбрасывается однозначная другая модель той же серии либо явно
подписанная другая модель. Общие каталоги, неоднозначные названия и ссылки
с присутствующей целевой моделью сохраняются. Параметры URL не анализируются
и не публикуются. Название ссылки никогда не подтверждает применимость паспорта.
Пропуск сохраняет безопасный код и hostname, не расходует download/VLM квоты.

Метрики `downloads_in_run`, `download_limit_per_run`, `run_number` описывают
текущий ограниченный запуск; `downloads` остаётся суммарным за все продолжения.
Попытки загрузки не называются успешно проверенными документами.
Задание с `not_found` заканчивается как `incomplete`, чтобы разрешённое
явное продолжение оставалось доступным и при пустой поисковой выдаче.

Проверяется буквальная модель, нужное исполнение и артикул в одном фрагменте.
Исполнение соседней модели на том же листе не подтверждает применимость.
Подтверждённые серверные алиасы производителя учитываются и при текстовом,
и при адресном визуальном чтении. Для неоднозначной таблицы выбираются
страницы нужной модели; новый полный VLM проход проекта не выполняется.

SSRF, проверка всех DNS ответов, закрепление публичного IP, проверка TLS,
лимит размера и redirect сохранены. Между hostname разрешён только HTTPS
переход на точный, отдельно доверенный домен того же производителя.
Неизвестным поддоменам доверие не передаётся. `allow_unverified` относится
к одному заданию и не превращает pending источник в trusted.

Владельца hostname подтверждают trusted записи. Старые pending ассоциации
с ошибочно назначенным VLM производителем не подменяют владельца сайта.
Для поиска неизвестного производителя используются профили с подтверждённым
источником. Миграция `20261012_0005` добавляет проверенные сайты и алиасы,
сохраняя существующие решения о статусе, HTTP и доступности. Она переиспользует
существующего производителя с соответствующим алиасом.

Подтверждения реестра: [Болид](https://bolid.ru/files/373/566/rip_12_51_ret_jun_24.pdf),
[РИЭЛТА](https://rielta.ru/catalog/izveshchateli/optiko-elektronnye/piron-sh/),
[Аргус-Спектр](https://catalog.argus-spectr.ru/storage/app/uploads/public/641/d62/202/641d622021180068028552.pdf),
[Магнито-Контакт](https://m-kontakt.ru/file/detectors_21.pdf),
[Электротехника и Автоматика](https://omelta.com/dokumentatsiya/).
Это реестр источников; таблица «модель → производитель» не захардкожена.

Отдельные безопасные коды причин: `dns_error`, `network_error`, `tls_error`,
`http_error`, `redirect_blocked`, `url_blocked`, `file_too_large`,
`unsupported_file`, `manufacturer_mismatch`, `manufacturer_unknown`,
`model_mismatch`, `variant_mismatch`, `article_mismatch`, `extraction_error`,
`facts_unavailable`, `query_budget_exhausted`, `download_budget_exhausted`,
`vision_budget_exhausted`, `operation_timeout`. Диагностика содержит этап и
hostname, не raw исключение драйвера, секрет или URL с параметрами.

## Отчёт и Review

Сводка раздельно показывает распознанные вхождения, уникальные модели,
модели с поисковыми запросами и доступные сохранённые документы. Таблица
показывает причину, запросы, попытки загрузки, VLM и доказательства по модели.
Кэш не выдаётся за новый поиск. Pipeline сворачивается.

Зелёный означает подтверждённое сравнимое утверждение с документом;
оранжевый — неполную проверку или необходимость идентификации;
красный — установленное расхождение; серый — отсутствие запуска или
подтверждённых проектных данных. Один `incomplete` не означает нарушение.
Сохранённый документ скачивается через разрешение на конкретное задание.

Большой EQ продолжается после основного N/T/U/D/E анализа. Прогресс SSE
восстанавливается с монотонного ID; пользователь может отменить и продолжить
EQ отдельно. После продолжения старое terminal событие не закрывает новую
подписку. Исходный `result.json` не переписывается.

Gateway строит дополнение по серверной инвентаризации и выбранной сохранённой
версии EQ. Браузер передаёт только номера EQ и Review редакций. По явному
действию новые находки добавляются в Review как pending. Существующие
находки, решения, оригиналы и источники не меняются. Несколько новых находок
коммитятся одним CAS и одним событием с полным пакетом аудита. Повторное
добавление тех же ID идемпотентно. Утверждённый Review и старая ревизия
отклоняются. После добавления обновите Human Review для просмотра находок.
Основание нового EQ дополнения — документация производителя; оно не выдаётся
за найденный норматив N. Существующие N/T/U/D/E остаются независимыми.

## Проверки и выпуск

Сначала Windows quality, просмотр полного diff, пользовательский commit и
push в оба репозитория. Затем Linux quality со всеми изолированными PostgreSQL
и Qdrant тестами, миграция, выборочная пересборка, публикация обновлённого
существующего n8n workflow и ручная приёмка. Не проводите первое обновление
старого EQ сервиса с активными заданиями без checkpoint.

Полные серверные логи сохраняйте в `/tmp`, Windows-логи — в `$env:TEMP`;
передавайте только exit code,
числа passed/failed/skipped и блоки ошибок. Локальная проверка без Docker
не подтверждает реальные DB/GPU тесты.

Обновление справки и текущего улучшения кандидатов выполняется без миграций
и публикации n8n. План выборочной пересборки и HTTPS-приёмки:
[docs/help-center.md](help-center.md). Пользовательские объяснения:
[docs/user-guide.md](user-guide.md).

Ручная приёмка:

1. Новый анализ контрольного PDF с EQ: шесть уникальных моделей, нет
   самостоятельного Touch Memory и производителя «Рубеж» из предположения.
   Наименования и интерфейс показаны вместе с моделью, исполнение отдельно.
2. С включённым и выключенным разрешением неподтверждённых источников
   проверить доступ к trusted источникам; галка не снимается после запуска.
   Unverified источник сохраняет предупреждение и не становится trusted.
3. Таблица, фильтры, серые/оранжевые/красные статусы, причины и сохранённые
   PDF/HTML. Ошибка каждой модели видна отдельно, длинной простыни нет.
4. Спецификации на 300 и 500 позиций: основной анализ завершён, EQ работает
   в фоне; первая попытка у всех допустимых моделей раньше повторов. Отменить,
   обновить страницу, продолжить, перезапустить сервис между порциями.
5. Явно добавить новую EQ версию в Review; прежнее принятое замечание
   остаётся прежним, новые требуют решения. Другой владелец, guest, другая
   вкладка со старой версией и утверждённый Review не обходят защиту.
6. EQ off/on/cold/warm при одинаковых D/E и документах: измерить время,
   запросы, загрузки, долю подтверждённых документов, VLM/embedding вызовы,
   токены, пиковую VRAM и задержки. Нагрузку shared VLM проверять отдельно
   по [существующей инструкции](equipment-validation.md#нагрузочная-проверка-ограничителя-analysis).

Автотесты включают настоящий PDF с управляемым VLM, 300/500 моделей,
реальное JSONB сохранение порций, восстановление, отмену, CAS и Review аудит,
модель/исполнение/артикул, alias, CDN/SSRF, SSE и HTTP запрет браузерных
оригиналов. Испытания с реальным поиском и GPU не заменяются этими тестами.
