# Auth Service: вход и серверные сессии

`auth-service` проверяет учётные данные и создаёт непрозрачные серверные сессии.
`user-service` хранит профиль и права, `admin-service` выполняет административные
сценарии через API. Пароль корпоративной записи AD не записывается ни в один
сервис PDRD. Хеши локальных и email-паролей хранятся только в схеме `auth`.

## Корпоративный вход

Локальный Active Directory принят как источник идентификации сотрудников.
Адаптер выполняет LDAPS bind с проверкой сертификата и ищет запись по
экранированному `sAMAccountName`. Устойчивый ключ пользователя —
`(provider_id, namespace, objectGUID)`, а не логин, email или DN. Заблокированная
запись AD не допускается к входу. Роли назначаются локально в `user-service`;
`role_source=ad_group` зарезервирован, но пока не даёт полномочий.

Проверенные параметры находятся в `.env.example`: домен `itcneoterm.local`,
base DN `DC=itcneoterm,DC=local`, контроллер
`WIN-1L5FI1SGC9J.itcneoterm.local:636`. IP `192.168.10.5` справочный и не
подменяет DNS-имя сертификата. С Linux-сервера доступны DNS и TCP 636.

Сертификат контроллера обновлён и проверен 2026-10-02. Он выдан на
`WIN-1L5FI1SGC9J.itcneoterm.local`, действует с 2026-10-02 до 2027-10-02 и имеет
SHA-256 fingerprint
`82:F3:12:92:14:CC:A4:35:13:49:13:43:0F:4A:8B:22:DC:BC:C8:82:96:65:44:1D:C2:F5:D3:FF:A9:E8:3C:2E`.
Проверка `openssl s_client` подтвердила TLS 1.2, цепочку и hostname.

Корневой `itcneoterm-WIN-1L5FI1SGC9J-CA-2` установлен в системное хранилище
Linux; его SHA-256 fingerprint —
`3B:2B:E1:78:F1:58:8D:D3:F1:F6:F4:9F:14:A0:DC:3A:20:61:DB:83:B7:D3:87:56:BE:02:3E:20:E4:5A:D4:EB`.
Системное хранилище хоста не передаётся контейнеру автоматически, поэтому
публичный CA bundle дополнительно размещается как `ops/certificates/ad-ca.pem`.
Compose монтирует каталог только в `auth-service` read-only, а контейнер читает
`/run/pdrd-auth-certificates/ad-ca.pem`. Закрытый ключ контроллера сервису не
передаётся. Файл сертификата окружения игнорируется Git.

После установки CA bundle корпоративный адаптер можно включить через
`AUTH_SERVICE_ENABLED=true`. `scripts/up.sh` отклоняет включение без этого файла,
а TLS-клиент строго проверяет цепочку и DNS-имя. Автоматические LDAP-тесты
используют подмену адаптера; отдельная runtime-приёмка должна подтвердить bind
реальной учётной записью без вывода или сохранения её пароля.

## Внешняя регистрация и сессии

Внешний пользователь регистрируется через email и пароль. Подтверждение email
отправляется SMTP на указанный адрес; до подтверждения вход не выдаёт рабочую
сессию. После первого подтверждения email User Service атомарно назначает уровень
`member`, роль «Проектировщик» и все текущие разделы. Первое создание профиля
после успешного AD-входа использует ту же первичную политику. Вход существующего
пользователя не сбрасывает вручную изменённые роли и назначения. Неподтверждённая
регистрация не даёт рабочей сессии. Собственные пакеты и рабочий промпт доступны
в назначенных разделах; чужие пакеты и администрирование недоступны.

Сессия выдаёт браузеру `HttpOnly` cookie с `Secure` и проверяется через
`auth-service` при каждом защищённом действии. В PostgreSQL хранится только
хеш случайного секрета сессии. Сервис сверяет статус профиля и
`authorization_version` с `user-service`: блокировка или смена роли прекращает
действие старой сессии. AD при обычном запросе не вызывается. Поддерживаются
выход, выход со всех устройств и отзыв выбранной собственной сессии.

Обычный срок сессии ограничен политикой неактивности и абсолютным максимумом.
Отдельный ротируемый 30-дневный grant «Запомнить меня» пока не реализован и не
показывается как действующая возможность.

## Публичная и внутренняя границы

Браузер вызывает только маршруты Gateway `/api/v1/auth/*` и
`GET /api/v1/users/me`. Gateway пересылает допустимые заголовки без клиентского
`Authorization` или поддельного Actor ID. Изменяющие запросы требуют Origin и
CSRF. Закрытый `/internal/v1/auth/introspect` доступен только сервисам с
отдельным ключом. Недоступность Auth или User Service закрывает защищённый
доступ, а неверная cookie не превращается в гостя.

Профиль Compose `auth` запускается вместе с `identity` и включает миграцию,
`auth-service` и `admin-service`. `scripts/up.sh` проверяет согласованный публичный origin,
ключи и SMTP-реквизиты из закрытого `.env`; `scripts/check-stack.sh` проверяет
контейнеры, миграции и HTTP readiness. Несекретные значения читаются из
`.env.example`, секреты переопределяются в `.env`. Для Yandex SMTP используются
`AUTH_SERVICE_EMAIL__SMTP_HOST=smtp.yandex.ru`, порт 465 и SSL; в `.env`
нужно задать `AUTH_SERVICE_EMAIL__SMTP_USER`,
`AUTH_SERVICE_EMAIL__SMTP_PASSWORD`, `AUTH_SERVICE_EMAIL__FROM_EMAIL` и
`AUTH_SERVICE_EMAIL__PUBLIC_BASE_URL` с тем же публичным origin.
HTTP-порт frontend по умолчанию привязан к `127.0.0.1`. Рабочие окружения
stage/prod требуют HTTPS и Secure cookie; точный Origin и CSRF обязательны.
Браузерный клиент блокирует вход и регистрацию на HTTP до отправки пароля.
Временный адрес `http://192.168.55.3:8080` не предназначен для входа.
Предложение настройки HTTPS через Nginx существующего frontend описано в
[схеме локального HTTPS](identity-https.md).

## Локальный суперпользователь и выбор источника входа

Первый администратор создаётся серверной командой без AD, email и UUID:

```bash
bash scripts/create-superuser.sh
```

Команда вызывает Python внутри auth-service с TTY, запрашивает имя
(`admin` по умолчанию), скрытый пароль и подтверждение. Пароль должен содержать
12–1024 символа. Профиль `kind=local`, уровень `member`, роль `platform_admin`
и одноразовый guard сохраняются атомарно в users. Пароль хешируется scrypt
в auth.local_credentials; каталог пользователей не получает пароль или хеш.

Сервис сначала находит профиль в user-service. Локальный источник проверяет
свой пароль, email-источник — подтверждённую внешнюю учётную запись, корпоративный
источник — каждый раз проверяет AD. Неверный локальный пароль не переключает
вход на AD. Первый успешный вход AD идемпотентно создаёт профиль по
`(provider_id, namespace, objectGUID)`; повторный вход возвращает прежний UUID.
Пароль AD и его хеш не сохраняются. Неизвестный короткий логин проверяется в AD;
неизвестный email проверяется контуром email-регистрации. Сообщение при отказе
предлагает проверить данные либо зарегистрироваться, не раскрывая наличие аккаунта.

При сбое между созданием профиля и завершением привязки локального пароля
команду можно повторить с прежним именем и паролем: используется тот же subject.
Незавершённая запись не допускает вход. После успешного bootstrap другие
администраторы и рабочие роли назначаются действующим администратором в админке,
с аудитом и CAS. Снятие собственных административных прав запрещено.

## Изоляция общей инфраструктуры при запуске

`scripts/up.sh` сохраняет Compose namespace PDRD, но очищает унаследованные
`COMPOSE_*` только в дочерних shell общей инфраструктуры. Поэтому shared
Compose читает собственные project name, profiles и env-файлы. Эта граница
применяется и к запуску shared, и к командам RabbitMQ. Docker context сохраняется.

Перед изменением инфраструктуры скрипт читает Docker labels и останавливается,
если `rabbitmq`, `n8n-db` или `n8n` ошибочно находятся в namespace PDRD.
Это не позволяет удалить их автоматически как orphan-контейнеры. Для ручного
восстановления сначала проверяют service/project labels, путь Compose и mounts;
широкие `down`, `prune` и удаление volumes для этого не используются.

## Проверка корпоративного входа на сервере

Системное доверие Linux не заменяет CA bundle контейнера. Перед включением AD
публичный сертификат CA устанавливается в игнорируемый Git файл:

```bash
install -m 0644 \
    /home/main/itcneoterm-ca-2.crt \
    ops/certificates/ad-ca.pem
```

После настройки профилей, служебных ключей, SMTP и CA нужно согласовать адрес
браузера с Auth/Gateway/email. Скрипт атомарно меняет только связанные параметры
закрытого .env, не выводит его содержимое и сохраняет остальные строки:

```bash
python3 scripts/configure_auth_origin.py https://pdrd.itcneoterm.local
bash scripts/up.sh
bash scripts/create-superuser.sh
```

`scripts/up.sh` применяет обе новые миграции и пересоздаёт сервисы с новым
окружением. Затем браузер открывается по точно указанному адресу. При смене
cookie-политики выполните новый вход.

Проверка локального суперпользователя и полного маршрута frontend/Gateway/Auth:

```bash
python3 scripts/check_auth_runtime.py --transport-url https://pdrd.itcneoterm.local --public-origin https://pdrd.itcneoterm.local --login admin --expect-admin
```

Корпоративный вход проверяется аналогично с `--login i.mein`. До назначения
ему admin-роли параметр `--expect-admin` не указывается. Пароль запрашивается
скрыто. Transport проверки остаётся `http://127.0.0.1:8080` на сервере;
удалённый HTTP transport скрипт не разрешает.

Публичный origin задаётся только как HTTPS. Cookie остаётся Secure; режима
ослабления безопасности для корпоративного HTTP-входа нет.

Изолированные интеграционные проверки миграций и транзакций:

```bash
docker compose -p pdrd-user-service-test -f ops/compose.user-test.yaml up --build --abort-on-container-exit --exit-code-from user-test-runner
docker compose -p pdrd-user-service-test -f ops/compose.user-test.yaml down
docker compose -p pdrd-auth-service-test -f ops/compose.auth-test.yaml up --build --abort-on-container-exit --exit-code-from auth-test-runner
docker compose -p pdrd-auth-service-test -f ops/compose.auth-test.yaml down
```


## Ошибка проверки готовности frontend

Если контейнеры готовы, а frontend возвращает `HTTP 000`, сверяют
`FRONTEND_BIND_IP` и `FRONTEND_PORT` с опубликованным адресом контейнера.
Публикация на `192.168.55.3:8080` не означает, что порт слушает
`127.0.0.1:8080`. `check-stack.sh` учитывает выбранный адрес;
`0.0.0.0` и `::` проверяются через соответствующий loopback.
При ошибке выводится проверяемый URL.

`scripts/up.sh` собирает образы один раз, затем повторяет проверку готовности
до таймаута. После исправления адреса достаточно выполнить
`bash scripts/check-stack.sh` без повторной сборки.
Если auth/user готовы и миграции применены, первый администратор создаётся
через `bash scripts/create-superuser.sh` независимо от общей проверки.
Вход из браузера проверяется после подготовки HTTPS.
