# Auth Service: вход и серверные сессии

`auth-service` проверяет учётные данные и создаёт непрозрачные серверные сессии.
`user-service` хранит профиль и права, `admin-service` выполняет административные
сценарии через API. Пароль корпоративной записи AD не записывается ни в один
сервис PDRD. Хеш пароля внешнего пользователя хранится только в схеме `auth`.

## Корпоративный вход

Локальный Active Directory принят как источник идентификации сотрудников.
Адаптер выполняет LDAPS bind с проверкой сертификата и ищет запись по
экранированному `sAMAccountName`. Устойчивый ключ пользователя —
`(provider_id, namespace, objectGUID)`, а не логин, email или DN. Заблокированная
запись AD не допускается к входу. Роли назначаются локально в `user-service`;
`role_source=ad_group` зарезервирован, но пока не даёт полномочий.

Проверенные параметры находятся в `.env.example`: домен `itcneoterm.local`,
base DN `DC=itcneoterm,DC=local`, контроллер
`WIN-1L5FI1SGC9J.itcneoterm.local:636`. IP `192.168.10.5` справочный и не
подменяет DNS-имя сертификата. Контейнеру нужен доверенный CA-файл через
`AUTH_SERVICE_AD__CA_BUNDLE_PATH`. До проверки доступа, SAN сертификата и CA
именно из Linux-контейнера AD-вход не следует включать. Тесты LDAP используют
подмену адаптера и не подтверждают соединение с боевым контроллером.

## Внешняя регистрация и сессии

Внешний пользователь регистрируется через email и пароль. Подтверждение email
отправляется SMTP на указанный адрес; до подтверждения вход не выдаёт рабочую
сессию. После подтверждения бесплатный аккаунт получает возможности гостевого
анализа без Review, пользовательских пакетов и администрирования.

Сессия выдаёт браузеру `HttpOnly` cookie с `Secure` и проверяется через
`auth-service` при каждом защищённом действии. В PostgreSQL хранится только
хеш случайного секрета сессии. Сервис сверяет статус профиля и
`authorization_version` с `user-service`: блокировка или смена роли прекращает
действие старой сессии. AD при обычном запросе не вызывается. Поддерживаются
выход, выход со всех устройств и отзыв выбранной собственной сессии.

Обычный срок сессии ограничен политикой неактивности и абсолютным максимумом.
Отдельный ротируемый 30-дневный grant «Запомнить меня» пока не реализован и не
показывается как действующая возможность.

## Публичная и внутренняя границы

Браузер вызывает только маршруты Gateway `/api/v1/auth/*` и
`GET /api/v1/users/me`. Gateway пересылает допустимые заголовки без клиентского
`Authorization` или поддельного Actor ID. Изменяющие запросы требуют Origin и
CSRF. Закрытый `/internal/v1/auth/introspect` доступен только сервисам с
отдельным ключом. Недоступность Auth или User Service закрывает защищённый
доступ, а неверная cookie не превращается в гостя.

Профиль Compose `auth` запускается вместе с `identity` и включает миграцию,
`auth-service` и `admin-service`. `scripts/up.sh` проверяет HTTPS origin,
ключи и SMTP-реквизиты из закрытого `.env`; `scripts/check-stack.sh` проверяет
контейнеры, миграции и HTTP readiness. Несекретные значения читаются из
`.env.example`, секреты переопределяются в `.env`. Для Yandex SMTP используются
`AUTH_SERVICE_EMAIL__SMTP_HOST=smtp.yandex.ru`, порт 465 и SSL; в `.env`
нужно задать `AUTH_SERVICE_EMAIL__SMTP_USER`,
`AUTH_SERVICE_EMAIL__SMTP_PASSWORD`, `AUTH_SERVICE_EMAIL__FROM_EMAIL` и
`AUTH_SERVICE_EMAIL__PUBLIC_BASE_URL` с тем же HTTPS origin.
HTTP-порт frontend по умолчанию привязан к `127.0.0.1`; внешний доступ должен
проходить через настроенный HTTPS reverse proxy с тем же публичным origin.

Для первого администратора используется однократная серверная bootstrap-команда
после создания подтверждённого корпоративного профиля. Она не является
публичным HTTP-маршрутом. Настоящий AD-вход и доставка писем требуют отдельной
проверки на Linux после настройки сети, CA и SMTP.
