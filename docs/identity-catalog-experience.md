# Разделы, авторы Experience и первичный доступ

## Рабочая политика

| Действие | Проектировщик | Руководитель отдела | Администратор |
| --- | --- | --- | --- |
| Создать раздел | Нет | Да | Да |
| Переименовать назначенный раздел | Нет | Да | Да, любой раздел |
| Удалить раздел вместе с документами | Нет | Нет | Да |
| Читать каталог Experience и фильтровать по автору | Нет | Да | Да |
| Изменять замечания и управлять версиями Experience | Нет | Нет | Да |

Сервер проверяет permissions и назначенный раздел. Скрытые кнопки отражают эти
проверки. Личные пакеты сохраняют отдельную проверку `owner_user_id`: роль
руководителя/администратора не открывает чужие пакеты. Обычный PDF/CAD без раздела
остаётся доступен гостю и вошедшему пользователю.

## Создание и назначения

Knowledge Service создаёт раздел. Gateway передаёт его UUID в закрытый сценарий
User Service от имени подтверждённого пользователя. Текущие `normative.write`
проверяются повторно; UUID актёра из браузерного тела/заголовка не используется.
Новый раздел добавляется всем активным проектировщикам и руководителям, включая
создателя. Существующие назначения и роли сохраняются. Администратор имеет все
разделы без отдельных грантов.

Журнал `users.catalog_section_distributions` делает выдачу одноразовой. Сбой
транзакции откатывает назначения и журнал, позволяя безопасно повторить выдачу.
Повтор завершённой выдачи не восстанавливает последующий ручной отзыв доступа.
Автоматическое добавление раздела сохраняет текущую `authorization_version`,
поэтому действующие сессии продолжают работать. Ручная смена роли/разделов
сохраняет CAS, аудит и отзыв прежней версии сессии.

Первый успешно подтверждённый AD-профиль и первое подтверждение email получают
уровень `member`, локальную роль `designer` с областью `own` и все текущие
разделы. Неподтверждённый email остаётся без рабочей роли. Всё первичное назначение
сохраняется одним переходом версии 1 → 2 и двумя аудитами в одной транзакции.
Повторный вход существующего профиля не возвращает снятые права и не заменяет
его роль. Старые профили автоматически не преобразуются: ими управляют через
админку. Общая блокировка каталога и завершённые выдачи закрывают гонку первого
входа с одновременным созданием нового раздела.

User Service читает Knowledge через HTTP-порт без SQL к чужой схеме. При
недоступности каталога новый профиль/подтверждение получает 503 без частичной
записи. Повторный вход существующего профиля не читает каталог.

Создание раздела и выдача грантов принадлежат разным сервисам. При отказе RPC
Gateway возвращает 503 с `section_id` уже созданного раздела; автоматического
повторного создания нет. После восстановления User Service нужно повторить
выдачу для этого UUID, не создавать второй раздел. Серверная процедура:

```bash
# SECTION_ID: UUID из ответа 503; ACTOR_ID: UUID действующего руководителя/админа.
SECTION_ID='вставьте-UUID-раздела'
ACTOR_ID='вставьте-UUID-пользователя'
docker compose --profile identity exec -T user-service python - "$SECTION_ID" "$ACTOR_ID" <<'PY'
import asyncio
import sys
from uuid import UUID
from pdrd_user_service.core.container import build_container

async def main():
    container = build_container()
    try:
        result = await container.section_distribution.execute(
            section_id=UUID(sys.argv[1]), actor_user_id=UUID(sys.argv[2]),
        )
        print(result)
    finally:
        await container.close()

asyncio.run(main())
PY
```

## Удаление раздела

Gateway допускает DELETE только с `normative.delete` администратора или пользователя
с явным назначением и доступом к разделу. [Правила назначения](normative-access-rejection-feedback.md). Knowledge
берёт эксклюзивную блокировку UUID раздела; HTTP-загрузки и нормативные
индексаторы держат совместную блокировку. После завершения текущей индексации
раздел получает постоянную отметку `deleting=true`, запрещающую новые загрузки,
папки, переименование, индексацию и снимки анализа с этим разделом.

Очистка удаляет документы обеих областей: нормативку и все личные пакеты внутри
раздела. Для каждого документа удаляются точки Qdrant, оригинал и PDF
предпросмотра. Затем удаляются осиротевшие точки по `section_id`, вся проверенная
папка UUID и строки SQL с каскадом категорий. Общая коллекция Qdrant сохраняется:
в ней находятся другие разделы. Путь с перенаправлением через символическую
ссылку отклоняется до удаления.

Внешний сбой оставляет отметку удаления и ещё нужные метаданные. HTTP возвращает
503 с предложением повторить удаление; UI не позволяет использовать раздел для
анализа, но оставляет администратору кнопку повтора. Повтор DELETE продолжает
очистку. Уже отсутствующий раздел также возвращает успешное подтверждение.
Прежние снимки заданий анализа не переписываются удалением каталога.

## Автор сохранённого замечания

Источник авторства — неизменяемый `source.created_by = user:<UUID>` из
подтверждённой сессии при сохранении. Редактор замечания не становится автором.
Gateway получает логин, отображаемое имя и **текущие** роли из User Service;
профили не копируются в исторический снимок. Колонка «Автор» и выпадающий фильтр
показывают логин, имя и русское название роли. Фильтр использует точное значение
авторства, а не изменяемое имя.

Старые записи с `engineer:...` сохраняются и фильтруются по исходному значению;
по похожему логину они не привязываются к UUID. При недоступности профилей каталог
остаётся читаемым, показывает исходный идентификатор и явное сообщение.
Тело запроса профилей ограничено 100 UUID; страницы авторов читаются последовательно.

Руководитель видит блок «База опыта» на главной странице и каталог, включая
историю замечания. Управление версиями, индексацией и административные правки
сохраняют отдельные права администратора.

## Проверки перед публикацией

На Windows из корня проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\ops\check-quality.ps1
```

Скрипт проверяет зависимости, Ruff, форматирование, весь pytest, frontend-тесты
и пробелы Git. Он не индексирует, не коммитит и не делает push. Реальные
PostgreSQL/Qdrant проверки выполняются отдельно; пропуск в обычном pytest
не означает проверку миграции или конкурентных транзакций.

## Обновление aistation

После проверки, коммита и push пользователя выполните блок целиком. Имена
тестовых Compose проектов заданы явно и не наследуют рабочий namespace.
Временные PostgreSQL/Qdrant не имеют host-портов, рабочих томов или сетей.

```bash
bash <<'BASH'
set -euo pipefail
cd ~/projects/PDRD-validation
[[ "$(git branch --show-current)" == feature/auth-user-admin ]]
if [[ -n "$(git status --porcelain)" ]]; then
    printf '%s\n' 'Рабочее дерево изменено: сначала разберите git status.' >&2
    exit 1
fi
git pull --ff-only origin feature/auth-user-admin
run_database_tests() {
    local project="$1" config="$2" runner="$3" result=0
    docker compose -p "$project" -f "$config" up --build --abort-on-container-exit --exit-code-from "$runner" || result=$?
    docker compose -p "$project" -f "$config" down
    return "$result"
}
run_database_tests pdrd-user-service-test ops/compose.user-test.yaml user-test-runner
run_database_tests pdrd-knowledge-service-test ops/compose.knowledge-test.yaml knowledge-test-runner
run_database_tests pdrd-experience-service-test ops/compose.experience-test.yaml experience-test-runner
# Старый индексатор не должен писать векторы без новой блокировки раздела.
docker compose stop knowledge-indexer
bash scripts/up.sh
bash scripts/check-stack.sh
BASH
```

`up.sh` пересобирает образы, применяет миграции и запускает все выбранные в `.env`
профили. Перед обновлением сохраняйте текущие `identity,auth,review` и остальные
используемые профили. Нужны новые версии Knowledge service/indexer и Gateway
вместе; ручное обновление только frontend недостаточно. Ожидаемые ревизии:
Knowledge `20261006_0006`, User `20261006_0006`. Experience не требует новой миграции.

Новое значение по умолчанию уже есть в Compose:
`USER_SERVICE_KNOWLEDGE_SERVICE_URL=http://knowledge-service:8401`.
Ключи, корпоративный TLS proxy и настройки HTTPS менять не нужно.
Secure/HttpOnly cookie, CSRF, строгий Origin и отсутствие хранения пароля AD
сохранены.

## Ручная приёмка

1. Через `https://pdrd.itcneoterm.local/` войдите руководителем: видны «+ Раздел»,
   «Переименовать» и блок «База опыта»; удаления нет. Создайте тестовый раздел.
2. В уже открытых сессиях активного проектировщика и другого руководителя
   обновите каталог. Новый раздел доступен; повторный вход не требуется.
   В админке их чекбоксы нового раздела отмечены, прежние назначения сохранены.
3. Войдите ранее не использовавшимся AD-пользователем: роль «Проектировщик»,
   все действующие разделы назначены. Аналогично проверьте новую регистрацию
   с подтверждением email. Неподтверждённый email не допускается к входу.
4. Снимите у этого пользователя один раздел/измените роль в админке. После
   повторного входа прежнее автоматическое назначение не восстанавливается.
5. Руководителем откройте Experience. В колонке и фильтре «Автор» видны логин,
   имя и роль. Выбор автора оставляет только его записи. Смена роли автора
   обновляет отображение после загрузки страницы; редактирование записи админом
   не меняет автора. Кнопок управления версиями и удаления у руководителя нет.
6. В тестовый раздел загрузите нормативный PDF/Word, создайте личный пакет,
   дождитесь индексации. Администратором удалите раздел после предупреждения.
   Раздел, его папки, документы, предпросмотры и точки исчезают, соседний раздел
   остаётся рабочим. Повтор DELETE возвращает успех. Физические проверки
   PostgreSQL, Qdrant и файлов также выполняет изолированный Knowledge runner.
7. Гостем и вошедшим пользователем повторите обычный PDF/CAD без раздела:
   анализ запускается. Чужой личный пакет по-прежнему недоступен.

## Отдельное назначение ревью

Доступ проектировщика к ревью теперь выдаёт администратор. Правила назначения,
проверки и обновление описаны в [инструкции доступа к ревью](identity-review-access.md).
